# v2.4.1 节点类型规范名重命名 + 迁移向导放开 MySQL + 接管/追平缺陷修正

> 镜像标签：`custos-server:v2.4.1`
> 版本号唯一来源：`.env` 的 `VERSION=v2.4.1`（`scripts/deploy.sh` / `Makefile` / `docker compose` / 应用内 `config.APP_VERSION` 均从此读取）

---

## 一、本期主线

### 1. 节点类型规范名重命名（方案 B）
- 规范名：`mysql8`→`mysql`（裸机 MySQL 8.0）、`mysql8-docker`→`mysql-docker`（容器化 MySQL 8.0）；原 `docker` 降级为历史别名（→`mysql-docker`），统一经 `normalize_node_type` 归一。
- 默认部署形态翻为 `mariadb-docker`（与接管路径默认对齐）。
- 存量 `node_type='docker'` 行**不 UPDATE**，靠别名兼容（避免误改成 `mariadb-docker` 导致引擎错配）。
- 引擎 flavour 常量 `F_MYSQL8="mysql8"` 保持不变（只改 node_type 命名空间，不动 `detect_flavour`）。

### 2. 数据迁移向导放开 MySQL
- 源/目标形态下拉放开 `mysql` / `mysql-docker`；`autoTarget()` 接受并归一旧别名（`docker`/`mysql8`/`mysql8-docker`）。
- 创建请求 `tgt_flavor` 按选中目标形态推导（mysql/mysql-docker→`mysql`，否则 `mariadb`），修正此前写死 `mariadb` 导致 MySQL→MySQL 逻辑迁移被 `_cap_of` 误判跨引擎而 `refused`。
- 约束（设计内，来自 `capabilities()`）：MySQL 目标只能走逻辑通道（mariabackup 是 MariaDB 专属）；bridge（live 追平）仅 MariaDB→MariaDB；MySQL 8.0+→MariaDB 源仍 `refused`。

### 3. 旧集群接管（takeover）与迁移追平缺陷修正
- 接管 A/B 两模式设计内修正（sidecar 部署方式、缺失端点、翻转 VIP 按钮显隐等）。
- 迁移追平 bug 根治：`bridge()` 走 `detect_flavour + change_replication_sql`（MariaDB 分支带 `MASTER_SSL=0`）；物理通道 copy-back 后补齐目标账号（`_ensure_target_accounts`）；迁移锁定改为仅跳过 promote（不再整轮 `return`）。
- 注：「物理 cutover 后自动重建同集群兄弟节点（`AUTO_REBUILD_AFTER_MIGRATION`）」属 2.4.0 既有机制（根治 213 静默不一致），2.4.1 未改动，此处仅作说明。

---

## 二、升级指引

1. 拉取新代码（`.env` 已含 `VERSION=v2.4.1`）。
2. 重建管理器：`./scripts/deploy.sh up -d --build`。
3. 存量 `node_type='docker'` 节点**无需改库**，应用经别名自动归一；如需彻底清除别名，确认全环境无 `docker` 行后再删（见 `mysql_compat._NODE_TYPE_ALIASES`）。

---

## 三、已知遗留 / 待回归

- 接管 A/B 两模式端到端真机回归尚未跑；裸机 MySQL 8.0 安装/卸载脚本未上真机实测。
- 迁移两条基线（177→33 容器、177→203 裸机）在 2.4.1 改动后需回归验证。
- `custos-ha-v2.4.0` 维护分支按约定**不吸收 2.4.1 的 node_type 重命名**（其 node_type 体系不同）；但 2.4.0 既有的追平/接管修复（含物理 cutover 后自动重建同集群节点）本就已在该分支，`AUTO_REBUILD_AFTER_MIGRATION` 机制无需 2.4.1 再打。
