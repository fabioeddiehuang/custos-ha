## 一、版本定位

**把"生成后人工搬运"变成"注册即部署"**：补齐单元分发、镜像分发与就绪感知，让纳管体验接近 Zabbix（服务端注册 → 节点自举 → 自动上报就绪）。

## 二、功能规划

### F1. 节点单元分发 `P1`

- **功能目的（Why）**
  - 现状：`node_gen.generate_node()` 已生成**自包含单元目录**（`generated_nodes/<ip>/`），但**要人工拷贝到目标机**再执行 `docker compose up -d`。
  - 服务端无法知道节点是否真的部署了，只能被动轮询探测，"注册"与"实际起来"是脱节的。
- **功能目标（验收标准）**
  1. 提供单元包下载接口：`GET /api/nodes/{ip}/unit.tar`（或 zip）
  2. 生成**一行引导命令**（带一次性 token）：
     `curl -sSL http://<mgr>/api/nodes/<ip>/bootstrap.sh?token=xxx | sh`
     脚本完成：下载单元 → 建目录 → 准备日志目录 → `docker compose up -d` → 回执
  3. token 一次性 / 短期有效 / 绑定节点 IP，用后失效
  4. 页面可直接复制引导命令与下载链接
- **涉及模块**：`app/api.py`（新路由）、`app/node_gen.py`（打包）、新增 token 校验、`app/templates/nodes.html`
- **依赖**：**v2.3-F1 凭证加密**（明文凭证不可下发）
- **非目标**：不做服务端主动 SSH/SCP 推送（保持纯拉取模式，更安全、无需凭据）

### F2. 镜像分发 `P1`

- **功能目的（Why）**
  - 现状：keepalived 镜像 `custos-node:<版本>` 需目标机**本地 build**，或人工 `docker save/load` 搬运（代码注释已承认此痛点）。
  - 目标机无外网或编译环境时，节点起不来。
- **功能目标（验收标准）**
  1. 方案 A（推荐）：服务端提供内网 registry，节点 `docker pull` 获取 `custos-node:<ver>`
  2. 方案 B（离线兜底）：服务端托管 `custos-node:<ver>.tar`，bootstrap 脚本自动 `docker load`
  3. bootstrap 流程自动选择可用方案，失败给出明确指引
- **涉及模块**：`scripts/`（新增分发脚本或 compose 服务）、`app/api.py`（镜像包下载）、`app/node_gen.py`（compose 渲染支持 registry 地址）
- **依赖**：F1

### F3. 就绪回执 + deploy_state `P1`

- **功能目的（Why）**
  - 现状：节点是否可用全靠服务端**主动轮询探测**，无"注册 → 部署中 → 在线"的状态机；新节点生成后页面显示 down，直到探测成功，用户不知道是"没部署"还是"部署失败"。
- **功能目标（验收标准）**
  1. `nodes` 表新增 `deploy_state`（`registered` / `provisioning` / `online` / `failed`）+ `last_ready_at`
  2. 新增回执接口：`POST /api/nodes/{ip}/ready`（由 bootstrap 脚本或 agent 调用）
  3. 页面按状态区分展示：待部署 / 部署中 / 在线 / 部署失败（附失败原因）
  4. 长期无回执且探测失败 → 标记 `failed` 并提示
- **涉及模块**：`app/db.py`（加列）、`app/api.py`、`app/monitor.py`、`app/templates/nodes.html`
- **依赖**：F1

### F4. 部署态漂移提示 `P2`

- **功能目的（Why）**
  - 现状：服务端重新生成单元（改 VIP、改凭证、升版本）后，节点侧**不会自动应用**，需人工跑 `update-node.sh`；用户无从知晓哪些节点"配置已过期"。
- **功能目标（验收标准）**
  1. 记录节点"已部署单元"的指纹（hash），回执时上报
  2. 与服务端当前生成比对，不一致则在页面提示"配置有更新，待应用"
  3. 提供一键"重新生成并下载"入口（不自动远程执行）
- **涉及模块**：`app/node_gen.py`、`app/db.py`、`app/api.py`、前端
- **依赖**：F3

### F5. 裸机安装增强 `P2`

- **功能目的（Why）**
  - 现状：裸机 MariaDB 用 tarball 安装，受 glibc 版本限制；装不上只能改用容器形态，且支持的发行版有限。
- **功能目标（验收标准）**
  1. 覆盖更多发行版（Anolis / Ubuntu / CentOS / Rocky 等主流版本）
  2. 提供**离线包**安装路径（内网无可用源时）
  3. 与 systemd 集成（服务启停、开机自启、日志接入 journald）
  4. 安装失败给出明确的"建议改用容器形态"指引
- **涉及模块**：`app/node_assets/Install-ha-mariadb-Node.sh`、`app/node_gen.py`
- **依赖**：无

## 三、本期非目标

- 不做服务端主动推送安装（SSH / Agent 远程执行）
- 不做节点远程卸载（仍需人工执行 Uninstall 脚本）
- 不做批量注册（一次填多个 IP）
