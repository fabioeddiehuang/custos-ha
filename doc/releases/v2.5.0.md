## 一、版本定位

**把「生成后人工搬运 + SSH 登录节点」变成「Web 上全部搞定」。**

用户只需要在服务端主机完成安装，此后**所有节点操作都在 Web 管理器完成，不需要 SSH 上机**。

## 二、写代码前必读的铁律（全部由真实事故/决策固化）

| # | 铁律 | 由来 |
|---|---|---|
| 1 | **MariaDB 与 MySQL 是两个产品，口径绝对不能混**。MariaDB 侧一律 `mariadbd`（服务端进程）/ `mariadb`（客户端）/ `mariadb-dump` / `mariadb-binlog`；`mysqld` / `mysql` / `mysqldump` **仅在明确指 MySQL 产品线时使用** | 用户 2026-09-26 再次纠正；项目 `Install-ha-mariadb-Node.sh:116` 用的是 `mariadbd` |
| 2 | **改密单一写入口**：数据库账号密码**只由服务端直连主库 `ALTER USER`** + binlog 复制下发；**绝不在只读副本执行 CREATE/ALTER USER**（会与复制线程争用 `mysql.*` 元数据锁 → 复制死锁）。agent **不执行改密 SQL** | 免 SSH 改密设计 |
| 3 | **裸机 MariaDB 由生成的安装脚本全量安装**（`app/node_assets/Install-ha-mariadb-Node.sh`，tarball 装 12.3.3 + systemd + 自动重放 fix-node-creds.sql）。**不要另写数据库安装逻辑** | 用户 2026-09-26 纠正 |
| 4 | **镜像 tar 不得进入管理器镜像**：存宿主 `./images/` + compose 挂载，**`.dockerignore` 必须加 `images/`**（`COPY . .` 会把未排除目录整体打进镜像，曾致 1.27GB） | 镜像体积铁律 |
| 5 | **UI 绝不阻塞等待**：长任务立即返回 `task_id`，前端 1.5s 轮询；**首帧必须立刻有内容**（阶段文字 + 已等待秒数 + 心跳时间戳），否则用户会以为卡死 | 用户明确要求 |
| 6 | **高危操作防呆**：纯净重建（L3）**不得对当前主库执行**；需二次确认 + 输入节点 IP | 防全量丢数据 |
| 7 | **不靠清空 `current_master` 放行 VIP** —— 会打开脑裂口子，比中断更危险 | vip-guard 防脑裂设计 |

## 三、功能规划

### F1 · 节点 curl 一行引导安装 `P0`

- **Why**：现状 `node_gen.generate_node()` 生成自包含单元目录后，要**人工拷贝**到目标机再 `docker compose up -d`。
- **验收**：
  1. `GET /api/node/bootstrap/<token>` 出安装脚本；`GET /api/node/bundle/<token>` 出单元包
  2. 页面给出**一行命令**（k3s 风格）：`curl -fsSL http://<mgr>/api/node/bootstrap/<token> | sudo bash`
  3. 脚本完成：下载单元 → 建目录 → 准备日志目录 → `docker compose up -d` → 回执上报
  4. **token 一次性 / 绑定节点 IP / TTL 默认 24h**（运维可能隔天才执行），用后失效；页面可随时「重新生成引导命令」
- **涉及**：`app/api.py`（新路由）、`app/node_gen.py`（打包）、token 校验、`app/templates/nodes.html`

### F2 · 镜像内部分发 `P0`（F1 的前置）

- **Why**：节点起 keepalived 需要 `custos-node:<ver>`（**本地构建**镜像，公网没有），agent 需要 `python:3-slim`（公共镜像，内网拉不到）。**不解决则 curl 引导会在 `docker compose up` 阶段失败。**
- **方案（用户已定：方案 B）**：服务端托管 `custos-node-<ver>.tar` + agent 镜像 tar，引导脚本 `docker load -i`（离线可用）。registry 方案留作可选开关。
- **何时需要重新固化镜像**：
  - keepalived 镜像（`app/node_assets/keepalived/Dockerfile` + 检查脚本 + entrypoint 变）→ 需要，跟随版本 tag
  - **agent 更新 → 不需要**：agent 是 `python:3-slim` **挂载** `node_agent.py`，改 agent 只下发文件 + 重启容器
- **涉及**：`scripts/`（构建脚本）、`app/api.py`（tar 下载）、`app/node_gen.py`（compose 渲染）

### F3 · 就绪回执 + deploy_state `P1`

- 节点 `deploy_state`（`registered` / `provisioning` / `online` / `failed`）+ `last_ready_at`；`POST /api/nodes/{ip}/ready` 回执。
- 页面区分「待部署 / 部署中 / 在线 / 部署失败（附原因）」。

### F4 · 配置漂移自动应用 `P1`

- 现状：重新生成单元后节点侧不会自动应用，只能人工跑 `update-node.sh`。
- 改为：指纹比对不一致 → **通过 agent 指令自动下发文件 + 重启服务**（F6 的 `update_files` / `restart_service`）。

### F5 · agent 心跳出向 + 指令通道 `P0`

- **通信方向**：agent → manager **心跳出向**（每 N 秒 POST），服务端在响应里**带回指令**；**同时保留** manager→node:28889 入向做即时操作，两者并存。心跳解决 NAT/单向防火墙 + 自注册。
- manager 地址为静态内网 IP，写死在 `agent.env`（由引导脚本写入）。
- **指令模型（用户已定）：模板化动词白名单**，参数严格校验转义：
  - `update_files` — 更新指定路径文件（b64），可带 `restart`
  - `restart_service` — 仅 `keepalived / agent / mariadb`
  - `set_credential` — 节点侧凭据文件 / agent token
  - `run_builtin_script` — 只跑随单元下发、带签名的内置脚本
  - `exec`（逃生舱）— **默认关闭**，`NODE_AGENT_ALLOW_SHELL=1` 才开，全审计
- **指令队列防惊群**：指令带**过期时间 + 限流**，管理器恢复后分批下发。
- **Why 白名单**：agent 是 root + `chroot /host` + `docker.sock` = 节点上帝权限。

### F6 · 免 SSH 改密 `P0`

- **三类密码分流**：

| 类别 | 谁改 | 通道 |
|---|---|---|
| ① MariaDB 账号密码（root / ha_monitor / replication / app） | **服务端直连主库** | `ALTER USER` → 复制下发 |
| ② 节点文件凭据（`ha_check.conf`、compose 的 `MYSQL_ROOT_PASSWORD`、keepalived 脚本） | agent | `update_files` + `restart_service` |
| ③ agent token | agent | `set_credential` |

- **顺序** `app → repl → ha_monitor → root`（root 最后，它是自愈回退凭据）
- **原子流程**：改 DB → 同步节点文件 → 重启 keepalived → 校验 → **任一失败回滚旧密码**
- **两个必坑**：
  1. **不同步 `ha_check.conf` → VIP 健康检查失败 → VIP 乱漂/双主**
  2. **改 compose 的 `MYSQL_ROOT_PASSWORD` 对已初始化数据卷不生效**，root 密码只能 `ALTER USER`
- **UI**：4 个账号带复选框 + 独立密码框；确认页明写「本次将修改：ha_monitor、replication（root、app 不变）」
- **改密期间自动短暂抑制告警 + 全程审计**

### F7 · 强制同步 / 切主就绪判定 `P0`

- **Why**：滚动升级时要「切主→更新旧主→再切」，但**不知道从库何时真追平**，靠猜易在未追平时切换 → 数据不一致/丢数据。
- **判据铁律**：**不能只看 `Seconds_Behind_Master=0`**（会骗人）。用 **GTID 集合比对**：MariaDB 主库 `@@gtid_binlog_pos` vs 从库 `@@gtid_slave_pos`，要求 `GTID_SUBSET(主库pos, 从库pos)=1`；再加**稳定采样**。
- **两档**：

| 档位 | 做法 | 业务影响 | 一致性 |
|---|---|---|---|
| 追平等待（默认） | 不停写，等追到延迟≈0 且 GTID 稳定 | 无 | 追平到某一刻 |
| **强制同步** | 主库置 `super_read_only=ON` 停写 → 等追平 → 报告完成 | 短暂阻塞写入 | 100% 一致 |

  - 锁写用 **`super_read_only`**（优于 `FLUSH TABLES WITH READ LOCK`，后者会锁长事务引发雪崩）
  - **强制档必须超时自动解锁**（默认 **120s**，可配，自适应 `max(120, 预估×1.5)` 封顶 600s）
  - **超时与库大小无关**，只取决于「从库落后多少」；启动前先**预估**，预估 > 超时则**直接拒绝启动**并提示先用「追平等待」
  - **稳定采样**：追平等待 **3 次 × 2s**（≈6s）；强制同步 **3 次 × 1s**
- **UI（绝不阻塞）**：点「强制同步」立即返回 task_id，前端 **1.5s 轮询**；显示还差多少事务/字节、预计剩余时间、进度条、**阶段文字**、**心跳时间戳**、**超时倒计时**；**「复制无进展」检测**（吞吐=0 且位点不变 → 提示可能卡在大事务/DDL）
- **与切换联动**：未就绪 → 「切换主库」置灰 / 二次确认 + 红字「还有 N 个事务未追平，切换将丢数据」；就绪 → 绿灯「✅ 同步完成，可以安全切换主库」
- **地基复用**：v2.4.0 一致性校验的 `_caught_up()` / `_wait_catch_up()` / 稳定采样 / verdict，**不重写**

### F8 · 滚动升级向导 + 节点修复分档 `P0`

- **入口**：**集群详情页新增 Tab「滚动升级」**（升级涉及切主 = 集群级动作，需集群上下文）；单节点操作仍留「节点管理」页。
- **流程**：选节点 → 选本次对每个节点做什么 → 逐个更新从库 → **强制同步** → 就绪绿灯 → 切换主库 → 更新旧主 → 降为从库 → 等追平 → 出报告
- **节点修复分档**：

| 档 | 做什么 | 现状 |
|---|---|---|
| L1 重启服务 | 重启 `mariadbd` / 容器 | 已有 |
| L2 重建复制 | 全量重新导入 + 清空自有 GTID 并对齐主库位点 | **已有**（`app/rebuild.py`，但不清数据目录） |
| **L3 纯净重建** | 停服务 → **清空数据目录/容器卷** → 重新初始化 → 全量导入 → 建复制 | **新增** |

  - L3 覆盖：数据库异常 / 重新安装 / 无法修复 / 必须纯净环境
  - **L3 锁定同版本 MariaDB 12.3.3，不做跨版本升级** → 不引入 `mariadb-upgrade`；但执行前**校验版本 == 集群期望版本**，不一致拒绝
  - L3 铁律：**目标节点不得是当前主库**（且集群须另有存活主库）；二次确认 + 输入节点 IP
- **L3 数据源（用户已定）**：**最近一次已有备份作基线 + binlog 增量回放**（不为重建现做备份）
  - `app/backup.py` meta **已记录 GTID 位点**（`gtid_binlog_pos` / `gtid_slave_pos`）与 `binlog_pos`，地基现成
  - 流程：取最近备份 → 恢复基线 → `mariadb-binlog` 回放「备份位点→当前」→ GTID 对齐（复用 `rebuild._align_gtid_after_restore`）→ 建复制
  - **加「优先从健康从库取基线」**（主库零压力）
  - **智能选路**：增量 > 全量数据量 **30%** 就改走全量 dump；无备份或 binlog 超保留期 → 回退全量
  - ⚠ **从备份恢复 ≠ 完整**，必须 binlog 补齐否则丢数据；"更安全"仅指不打扰主库。UI 必须写清

### F9 · 定时备份（集群级）`P1`

- **后端已有** `app/monitor.py:_maybe_scheduled_backup()`（settings 表，默认关闭）：`BACKUP_SCHEDULE_ENABLED` / `BACKUP_INTERVAL_HOURS`(24) / `BACKUP_RETENTION_DAYS`(7) / `BACKUP_TARGET`(slave) / `BACKUP_WITH_DATA`(1)；`_pick_backup_nodes()` **已实现优先从库、无从库回退主库**。
- **v2.5.0 补齐 3 项**：
  1. 配置入口从「系统设置（全局）」→ **集群管理 → 备份恢复页**，**集群级优先、未设回退全局**
  2. 保留机制补 **`BACKUP_RETENTION_COUNT`（默认 7 份）**；天数/份数**双条件**（满足任一即清理）
  3. 默认仍**关闭**，但备份页明示因果：「未开启 → 节点纯净重建将走全量，较慢」
- **清理铁律**：**永不删除最新一份**（防策略误配被清空）
- **补做错峰**：管理器停机错过窗口 → 恢复后补做，但**按集群错峰排队**；UI **明确显示下次执行时间**与「逾期补做计划：集群A 03:05、集群B 03:10…」
- **磁盘占用预警**（备份 + binlog 都会撑爆磁盘）
- **备份前先「追平等待」**，保证从库备份位点干净

### F10 · 集群接管（原 v2.4.1）`P1`

- 接管 = 纳管，**不重建**。三层：阶段 0 `probe`（只读）/ 阶段 1 `adopt`（建账号 + 登记 + 装 sidecar）/ 阶段 2 `extend`（单机场景开 binlog → 导出 → 导入 → 建复制）
- **装 sidecar 直接复用 F1 的引导命令**，不引入 SSH
- 硬约束：同集群同版本、server_id 非 0 且唯一、节点同二层网络（VRRP）
- 阶段 2 开关框架：不止 binlog——接管所需但 flavor 默认关的变量（`log_bin` / `gtid_domain_id` / `gtid_strict_mode` 等）一律做成**显式 opt-in 开关（带 restart 标记）**
- 详见 `doc/开发/v2.4.1-接管设计.md`（探测层 `app/adopt.py` 已实现）

### F11 · 计划内停机的「无保护窗口」提示 `P2`

- **事实**：管理器停机时 VIP 判据读**节点本地** `ha_local.state.current_master`，值不清空 → **主库健康则业务完全不受影响**；但**主库故障则无法自动切换**（从库因 current_master 仍指旧主而拒绝拿 VIP），即进入**无保护窗口**。
- 升级/停止管理器时输出醒目警告 + 仪表盘显示「管理器离线时长」。

## 四、本期非目标

- **不做管理器自身 HA**（用户决定不考虑；用 F11 提示 + 缩短停机窗口代替）
- **不做无 docker 环境的节点安装**（后续版本）
- **不支持 MariaDB 高于 12.3.3**（将来需要时再评估版本矩阵/能力表/方言）
- 不做 `mariabackup` 物理备份（镜像内没有，会撞镜像体积铁律，且未实测）
- 不做服务端主动 SSH/SCP 推送（保持纯拉取 + agent 心跳，更安全、无需节点凭据）
