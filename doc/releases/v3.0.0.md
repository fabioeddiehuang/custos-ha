## 一、版本定位

**从"能管好主从"走向"能看清、能升级、能编排"**：拓扑可视化、物理备份与 PITR、MariaDB 版本升级编排、兼容性预检，并同步推进平台化与 UI v3 改版。
这一版跨度大，建议**拆分为多个内部里程碑**分批发布，避免一次性大爆炸式升级。

## 二、功能规划

### F1. 拓扑可视化 + 拓扑 API `P1`

- **功能目的（Why）**
  - `failover.ensure_topology` 已有完整拓扑逻辑，但**没有对外 API、没有图形化**——用户只能看节点列表，看不出"谁挂谁、延迟多少、GTID 差多少"。
  - 这是 Orchestrator 的招牌能力，也是最强的"产品感"来源。
- **功能目标（验收标准）**
  1. 新增 `GET /api/topology/{cluster_id}`：返回树形结构（主 → 副本，含角色、延迟、只读状态、GTID 差距）
  2. 前端拓扑图：可视化展示复制方向与状态，点击节点可执行操作
  3. 与 UI v3 设计稿（`design/mockup_v3.html`）对齐
- **涉及模块**：`app/api.py`、`app/failover.py`、`app/ha_client.py`、前端拓扑组件
- **依赖**：无（数据现成）

### F2. mariabackup 物理备份 + 增量 + PITR `P1`

- **功能目的（Why）**
  - 现状仅有 Python 逻辑备份：大库（百 GB 级）导出导入极慢，且**无法做时间点恢复**。
  - MariaDB 官方工具 `mariabackup` 支持热备、增量、配合 binlog 做 PITR，是生产大库的刚需。
- **功能目标（验收标准）**
  1. 支持全量物理备份（mariabackup）与增量备份
  2. 支持**时间点恢复（PITR）**：恢复到指定时间点 / 指定 GTID
  3. 与现有逻辑备份共存：按数据量与场景选择策略，UI 可区分两类备份集
  4. 备份集统一纳入现有"备份历史 / 保留策略 / 校验"体系
- **涉及模块**：新增 `app/physical_backup.py`、`app/backup.py`（元信息统一）、`app/api.py`、备份页
- **依赖**：**v2.3-F2**（GTID / binlog 位点记录）
- **非目标**：MySQL 侧物理备份不做（MySQL 冻结）

### F3. MariaDB 版本升级编排 `P1`

- **功能目的（Why）**
  - MariaDB 官方**支持同族升级**（10.6 / 11.4 → 12.x，`mariadb-upgrade`），比 MySQL 5.7→8.0 现实得多，是刚需。
  - 但手工升级步骤多、易出错，且升级期间最怕自动切换插一脚。
- **功能目标（验收标准）**
  1. 升级计划：预检 → 备份 → 滚动升级（先副本后主库）→ 切换 → 验证 → 回滚
  2. 每步可暂停 / 重试，全程有进度与日志（复用 v2.4 任务中心）
  3. 升级期间自动进入维护模式（复用 v2.3-F3）
  4. 回滚路径明确：副本未升级即可回切；失败时用升级前备份恢复
- **涉及模块**：新增升级编排模块、`app/api.py`、`app/monitor.py`、前端向导
- **依赖**：**v2.3-F3 维护模式**、**v2.3-F2 备份位点**、v2.4 任务中心

### F4. 兼容性预检引擎 `P1`

- **功能目的（Why）**
  - 一套规则库可同时服务于三个场景：**版本升级**（F3）、**异构迁移**（MySQL→MariaDB）、**日常巡检**。
  - 现状 `precheck.py` 只覆盖连通性与复制参数，不足以支撑升级/迁移决策。
- **功能目标（验收标准）**
  1. 规则库按目标版本/目标引擎组织，输出「阻塞 / 警告 / 建议」三档报告
  2. 检查项覆盖：字符集与 collation、认证插件、数据类型（JSON 等）、权限名、`sql_mode`、存储过程/视图/触发器、废弃参数
  3. 报告可导出，供决策与留档
- **涉及模块**：`app/precheck.py` 扩展、新增规则库
- **依赖**：无（但 F3 依赖它）

### F5. MaxScale / 只读负载均衡 `P2`

- **功能目的（Why）**
  - 现状 VIP 只指向主库，**从库不承担读流量**，资源闲置；大查询也无法与写入隔离。
- **功能目标（验收标准）**
  1. 集成 MariaDB 官方代理 MaxScale（或自研轻量读 VIP），实现读写分离
  2. 读流量按策略分发到副本，副本异常自动摘除
  3. 与故障切换联动：切换后读流量自动重分布
- **涉及模块**：新增代理编排、`app/api.py`、节点部署模板（新增 MaxScale 单元）
- **依赖**：F1（拓扑数据）

### F6. 平台化 `P2`

- **功能目的（Why）**
  - 目前是"单管理员操作"的产品形态；团队协作、自动化对接、可追溯性不足。
- **功能目标（验收标准）**
  1. **API Token**：分 scope（只读 / 运维 / 管理），供脚本与 CI 调用
  2. **Webhook / Hook**：切换前后、备份失败等事件回调外部系统（工单、钉钉、企业微信）
  3. **结构化事件时间线**：切换 / 自愈 / 备份 / 告警 / 人工操作统一入事件流，支持检索与筛选
  4. 可选：多租户与项目分组、危险操作二次审批
- **涉及模块**：`app/api.py`、`app/auth.py`、`app/audit.py`、新增事件表
- **依赖**：v2.4 任务中心（统一事件来源）

### F7. UI v3 改版 `P2`

- **功能目的（Why）**
  - 现有 UI 为 v2 风格；v3 高保真稿已完成（`design/mockup_v3.html`），需落地以承载拓扑图、任务中心、升级向导等新能力。
- **功能目标（验收标准）**
  1. 按 `design/mockup_v3.html` 落地整体框架与视觉
  2. 承载 F1 拓扑图、任务中心、升级向导
  3. 保持暗/浅主题与响应式能力不退化
- **涉及模块**：`app/templates/`、`app/static/`
- **依赖**：F1

### F8. Galera Cluster（多主）专项评估 `P3`（仅评估，不在本期落地）

- **功能目的（Why）**
  - Galera 是 MariaDB 相对 MySQL 最独特的能力（真正的多主），诱惑大，但**是重构级工作**。
- **评估目标（本期只出结论，不写代码）**
  1. 现有概念不适用清单：主从切换、`Seconds_Behind`、`make_slave_of`、一致性校验、VIP 漂移逻辑
  2. 新增概念工作量：`wsrep_*` 状态、flow control、quorum 脑裂判定、SST/IST、gcache
  3. 目标客户是否真需要多主（避免为伪需求投入）
  4. 产出：是否立项、建议放在哪个版本
- **涉及模块**：仅评估文档，不改代码
- **依赖**：无
