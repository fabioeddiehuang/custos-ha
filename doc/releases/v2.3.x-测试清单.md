# v2.3.0 ~ v2.3.5 测试清单（含小白视角）

> 覆盖 2.3.x 全部新增功能。每个功能给三栏：
> **技术测法**（懂运维的人怎么验）、**小白怎么测**（看什么现象即可）、**验收勾选**。
> 部署步骤：`git pull` → `./deploy.sh up -d --build` → 看启动日志。

## 一、v2.3.0 · MariaDB 版本准绳 + 变更生效闭环

### F1 版本支持矩阵 / 版本感知
- **技术测法**：节点详情 `POST /api/node_detail` 连库取 `SELECT VERSION()`，回写 `nodes.mysql_version`；预检面板出现「版本准入」项，`<10.6` 报 ERR、10.6/10.11 给 WARN。
- **小白怎么测**：节点列表里每台 MariaDB 节点的「版本」列**不再是空白/未知**，会显示真实版本（如 `12.3.3`）。预检页面里能看到一条「版本准入」的检查项。
- **验收**
  - [ ] MariaDB 节点版本号自动显示，不手填
  - [ ] 预检出现「版本准入」项；低于 10.6 报红

### F2 变更生效提示（regen 动作清单）
- **技术测法**：regen 节点文件时 diff 新旧内容，产出 `pending_actions`（recreate/restart/exec/manual），每项带可复制命令；入库后节点列表显「配置待生效」徽标，点「已在节点执行」清零。
- **小白怎么测**：在节点页点「重新生成」，会出现一个**黄色「配置待生效」标签**；点开它，里面用大白话列出「你要在节点上做什么 + 复制即用的命令」。你在节点上照做后，回到页面点「已执行」，黄标消失。
- **验收**
  - [ ] regen 后出现「配置待生效」徽标
  - [ ] 清单含分级动作（重建容器 / 重启服务 / 节点执行 / 人工确认）与命令
  - [ ] 点「已执行」后徽标消失；配置再变则重新出现

### F3 半同步命名一致性
- **技术测法**：`mariadb_matrix.semisync_plugin_load()` 统一提供 `rpl_semi_sync_master/slave`；node_gen 与 ha_client 引用同一来源，无 source/replica 误改。
- **小白怎么测**：无需专门测——属防回归。只要「开半同步 → regen → 重建容器 → 复制正常、无节点启动即崩」即达标（见 v2.3.0 验收第 3 条）。
- **验收**
  - [ ] 半同步开关开启并重建容器后，节点复制正常、不崩

## 二、v2.3.1 · 凭证加密 + 密钥派生（SECRET_KEY）

- **技术测法**：设置页 `crypto.status()` 返回 `key_source=derived(SECRET_KEY)`（或 `env(CRED_KEY)`）；管理库 `nodes.root_pass` / `clusters.ha_pass/repl_pass/app_pass` 为 `ENC1:` 前缀密文；`query()` 透明解密，业务零改动；启动日志 `凭证加密迁移：已加密 N 条`（首次升级）。
- **小白怎么测**：
  1. 打开「设置 → 凭证加密」，看到绿色「**已开启**」状态，密钥来源写「由 SECRET_KEY 派生」。
  2. 平时**什么都不用做**——集群照常显示、照常连节点，密码在后台已是密文。
  3. 备份时**只用备份整个项目目录 / data/** 就行，不用单独管任何密码文件。
- **进阶（验证密钥确实绑定 SECRET_KEY）**：把 `.env` 里的 `SECRET_KEY` 改掉再重启 → 日志报「解密失败」，集群连不上节点；改回原值重启即恢复。（正常别这么干，仅验证用。）
- **验收**
  - [ ] 设置页显示「已开启 / derived(SECRET_KEY)」
  - [ ] 库里密码为 `ENC1:` 密文
  - [ ] 存量明文升级后自动迁移（启动日志可见）
  - [ ] 集群正常连接、Web 正常显示（解密通）

## 三、v2.3.2 · 备份一致性快照 + 位点入 meta

- **技术测法**：带数据全备在单 `REPEATABLE READ` 快照事务内完成；`*.meta.json` 含 `position`（MariaDB `gtid_binlog_pos/gtid_slave_pos`；MySQL `gtid_executed`+binlog file/pos）与 `consistent: true`；SQL 头注释写入位点。
- **小白怎么测**：备份页点「全量备份」→ 显示「成功」；点开某份备份的详情，能看到一行「**复制位点**」和「**一致性快照：是**」。老备份（无位点字段）仍能正常列出/预览/恢复。
- **验收**
  - [ ] 全备成功且 meta 含位点 + consistent=是
  - [ ] 老备份兼容可列/可恢复
  - [ ] （进阶）备份期间写入，恢复后跨表一致

## 四、v2.3.3 · 维护模式 begin / end

- **技术测法**：`maintenance` 表开窗口；`monitor` 主库失联切换前 `_in_maintenance` 拦截、延迟/压力整段跳过；`_alert_on_transition` 与 `alerts._deliver` 抑制状态类告警；放行关键字 `切换/数据冲突/备份失败/重建`；到期 `purge_expired` 兜底。
- **小白怎么测**：
  1. 集群卡片点「**进入维护模式**」→ 填原因/时长 → 卡片出现**「维护中」黄标**。
  2. 维护期间你去做重启节点、重建从库、升级等操作，**不会收到一堆「节点离线/复制中断/延迟过高」的告警邮件**（切主类也不会被自动触发）。
  3. 维护结束点「**结束维护模式**」→ 黄标消失，之后节点异常会正常告警。
- **验收**
  - [ ] 开窗口后卡片显「维护中」徽标
  - [ ] 维护期内关机/异常 → 状态类告警被抑制（不发邮件）
  - [ ] 切换类/人工处理类告警仍发
  - [ ] 到期或手动结束後恢复告警

## 五、v2.3.4 · 备份按库分文件 + index.json

- **技术测法**：多库（≥2）全备生成目录 `<label>_<ts>/`，内每库一个 `<db>.sql.gz` + `index.json`；`restore_backup` 识别目录按 `index.json` 逐库恢复；单库/指定库仍为单文件。
- **小白怎么测**：多库集群点「全量备份」→ 备份列表该条目带**「分库集」标签**和库数量；恢复时可单独勾选某个库，只恢复它（更快）。
- **验收**
  - [ ] 多库全备为目录形态（分库集 + index.json）
  - [ ] 单库/指定库仍为单文件（兼容）
  - [ ] 恢复指定库只读对应文件，成功

## 六、v2.3.5 · 三形态日志采集确认与提示

- **技术测法**：MariaDB 错误日志按 `@@system_time_zone` 换算时区（不差 8 小时）；读不到时 UI 给 `secure_file_priv`/`log_error`/FILE 权限实测值与修复步骤；慢日志空时 `_slow_log_hint()` 连主库查 `slow_query_log`/`log_output`/`long_query_time` 给原因。
- **小白怎么测**：
  1. 进「日志」页，即使没数据也**不是一片空白**——会显示明确的提示，如「慢日志未开启，去系统设置打开」「log_output 不含 TABLE，采集读不到」。
  2. 错误日志时间跟你本地时间**对得上**（不再差 8 小时）。
- **验收**
  - [ ] 慢日志为空时有明确「为什么空」提示
  - [ ] 错误日志读不到时有原因 + 修复指引
  - [ ] MariaDB 错误日志时区正确（不差 8h）
