# v2.3.1 ~ v2.3.5 变更记录（2.3.x 收官）

> 这五个小版本在 2.3.x 阶段一次性完成（用户要求「把 2.3.x 做完」）。
> 每一版都遵循「MariaDB 冒烟 + MySQL 回归」原则：MySQL 代码路径全程冻结或只做等价改造，
> 不得回归。版本号统一推进到 **v2.3.5**（`.env` 的 `VERSION=`）。
>
> 独立规划文档：v2.3.0 见 [v2.3.0.md](./v2.3.0.md)。

## v2.3.1 · 凭证明文加密（安全硬伤）

**Why**：`nodes.root_pass` 与 `clusters.ha_pass/repl_pass/app_pass` 长期明文入库。
任何能读 `custos_meta` 库的人（DBA、被入侵的节点、备份泄漏）都能直接拿到所有密码，
且 v2.5 单元分发要把凭证下发给节点，明文更是灾难。这是上线前必须堵的安全硬伤。

**What（验收）**
- 凭证**落库即密文**（`ENC1:` 前缀 + Fernet 对称加密），读取方**无感解密**；
- 存量明文在管理器启动（`init_schema()` 末尾）自动迁移为密文，业务代码零改动；
- 解密失败**返回空串 + ERROR 日志**，绝不静默回吐明文；
- 密钥 `data/cred.key` 缺失时自动生成（仅首次）。

**变更记录（Added / Changed）**
- **Added** `app/crypto.py`：Fernet 封装。密钥优先级 `CRED_KEY`(env) → `data/cred.key` → 自动生成；
  `encrypt()`/`decrypt()`/`is_encrypted()`/`status()`。前缀 `ENC1:` 防止对密文二次加密。
- **Changed** `app/db.py`：`query()` 按列名（`root_pass/ha_pass/repl_pass/app_pass`）自动解密；
  新增 `query_raw()`（迁移读原值用）、`migrate_encrypt_credentials()`（幂等自迁移，启动跑）。
- **Changed** 仅 **3 处**写入显式 `encrypt()`：`clusters.create_cluster`、`clusters.update_cluster`、
  `node_gen.generate_node`（INSERT 各账号口令）。13 个读取模块数百处调用**零改动**（靠查询层透明解密）。
- **Changed** `ha_client.load_creds` / 各 `execute` 写路径：写入时 `encrypt`，读取已透明。

**影响面**：只读库表、不碰节点。节点侧凭证不变（仍按原明文在节点执行 SQL，本机内存里短暂明文属正常）。
密钥文件 `data/cred.key` 必须随 `custos_meta` 库一起备份——丢了历史密文解不开（新密码照常可用）。

## v2.3.2 · 备份一致性快照 + 位点入 meta

**Why**：`run_backup` 用 `SHOW DATABASES` 后逐库开连接导出，**各库落在不同时点**——备份期间有写入，
恢复出来的跨表数据不一致（订单一笔、库存没扣）。且导出 **binlog 位点 与 数据不对应**，
无法做 PITR。这是正确性缺陷，是 v3.0 `mariabackup` + PITR 的地基。

**What（验收）**
- 带数据的全备在**同一 `REPEATABLE READ` 快照事务**内完成（跨表一致）；
- 备份 `.meta.json` 记录复制位点（MariaDB `gtid_binlog_pos/gtid_slave_pos`；
  MySQL `gtid_executed` + binlog file/pos）与 `consistent` 标记；
- 老备份（无 `position` 字段）仍可正常列出 / 预览 / 恢复（缺省兼容）。

**变更记录**
- **Added** `backup._capture_position(cur, flavour)`：快照内采位点。MariaDB 取 `gtid_binlog_pos`/
  `gtid_slave_pos`/`gtid_current_pos`；MySQL 取 `gtid_executed` + `SHOW MASTER STATUS`（8.4 回退
  `SHOW BINARY LOG STATUS`）。
- **Changed** `run_backup`：新建 `snap_conn` 执行 `SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ`
  + `START TRANSACTION WITH CONSISTENT SNAPSHOT`，**位点在该事务建立后采集**（保证位点不早于数据）。
- **Changed** `_dump_database(conn, cur, w, db, ..., data_conn=None)`：传 `data_conn` 复用快照连接
  —— **关键**：原来每库自建连接会落在不同时点快照，已修正为跨库共享同一快照。
- `meta` 增 `position` / `consistent` 字段；SQL 头写入位点与一致性标记注释。
- **Known Issues**：快照只覆盖数据读取；表结构（`SHOW CREATE TABLE`）在主连接读（无事务），
  极端的「备份期间改表结构」可能不一致（同 mysqldump --single-transaction 的已知限制，可接受）。

## v2.3.3 · 维护模式 begin / end

**Why**：做维护 / 重建从库 / 升级版本时，monitor 仍可能触发**自动切换**把正在操作的节点切走，
业务闪断、重建半途而废、告警刷屏。Orchestrator 等同类产品都有 `begin/end-maintenance`，
也是 v3.0「MariaDB 版本升级编排」的前置。

**What（验收）**
- 支持按 **集群 / 节点** 开维护窗口；到期自动结束（monitor 周期 `purge_expired` 兜底）；
- 窗口内**抑制自动切换**（主库失联 / 延迟压力）与**状态类告警**（离线/复制/延迟/半同步）；
- 切换类与「需人工处理」类告警**仍发**（维护期出事更要看得到）；
- 集群管理页有「维护中」徽标 + 开启/结束弹窗。

**变更记录**
- **Added** `app/maintenance.py` + `maintenance` 表（`scope` cluster/node、`end_at` 到期自动结束、
  `active` 标志）。`begin/end/is_in_maintenance/active_windows/summary/purge_expired`。
- **Changed** `monitor`：①主库失联自动切换前 `_in_maintenance(cid, key[0])`；②延迟/压力切换整段跳过；
  ③`_alert_on_transition` 开头按 `(cluster, host)` 抑制状态类告警。
- **Changed** `alerts._deliver`：**投递层兜底抑制**（最关键）——自愈观察期挂起的告警到点是直接走
  `_deliver` 的，只在 `send_alert` 判断会漏。放行关键字 `("切换","数据冲突","备份失败","重建")`。
- **Changed** `api.py`：`/api/maintenance`(GET) + `/api/maintenance/begin` + `/api/maintenance/end`；
  `_cluster_view()` 增 `maint` 字段。
- **Changed** `templates/clusters.html`：卡片「维护中」徽标 + 维护模式弹窗（范围/时长/原因/结束）。
- **决策**：维护判断异常时**一律按「不在维护」**——宁可多切一次，也不因维护表故障把「该切换却不切换」藏起来。

## v2.3.4 · 备份按库分文件 + index.json

**Why**：多库全备原来是一个大 `.sql.gz`。恢复指定库时得解压整库全集再按 `USE` 切段，
库多 / 库大时很浪费。分库文件让「恢复指定库」只读对应文件。

**What（验收）**
- 多库全备（≥2 库）自动走**目录模式**：`<label>_<ts>/` 内每库一个 `<db>.sql.gz` + `index.json`；
- 单库 / 指定库备份仍是单文件（兼容老备份）；
- 恢复指定库时只读对应文件（`restore_backup` 识别目录 → 按 `index.json` 逐库恢复）；
- 备份页标记「分库集」徽标。

**变更记录**
- **Changed** `run_backup`：多库全备改目录模式（每库文件独立 header + 一致性快照注释，共享 `snap_conn`）；
  抽出 `_write_backup_header`（两种形态共用）。
- **Changed** `restore_backup`：目录分派到新增 `_restore_backup_set`；抽出 `_exec_stmts`
  （单文件 / 目录恢复共用，含 `no_binlog` 会话级关闭）。
- **Changed** `list_backups`：增 `*/index.json` 目录扫描，统一 `kind=file|set`，按时间倒序合并；
  老备份按 `file` 处理。
- **Changed** `templates/backup.html`：「分库集」徽标 + 库数量展示。

## v2.3.5 · 三形态日志采集确认与明确提示

**Why**：错误日志 / 慢日志在 mysql-docker / mariadb-裸机 / mariadb-docker 三种形态下数据源不同，
读不到时前端只显示空白，运维无从下手。

**What（验收）**
- 错误日志：MariaDB（无 `log_timestamps`）按 `@@system_time_zone` 换算时区，**不再差 8 小时**；
- 读不到时 UI 明确给出原因（`secure_file_priv` 实测值 / `log_error` 未配置 / 无 FILE 权限）+ 修复指引；
- 慢日志为空时连主库查 `slow_query_log` / `log_output` / `long_query_time`，指出「`log_output` 不含
  TABLE 导致采集读不到」等真实原因。

**变更记录**
- **Changed** `api.py` 错误日志：MariaDB 无 `log_timestamps` → 改查 `@@system_time_zone` 判 UTC；
  兜底 `note` 列出 `secure_file_priv` / `log_error` 真实值，并给「设 `log_error` + `secure_file_priv=''`
  后重建容器」的修复步骤。
- **Changed** `api.py` 慢日志：空结果时 `_slow_log_hint()` 连主库查配置项，前端展示 `hint`。

## 升级说明（203 服务端）

**元数据库（custos_meta）无需重建**。所有 2.3.x 的库表改动都在 `init_schema()` 启动时自动幂等执行：
- v2.3.0 `nodes` 加列 + `mysql_version` 扩容；
- v2.3.3 新建 `maintenance` 表；
- v2.3.1 凭证加密是数据级 UPDATE（启动自动迁移明文→密文），无表结构变更。

步骤：`git pull` → `./deploy.sh up -d --build` → 看启动日志确认迁移完成。
**务必备份 `data/cred.key`**（凭证密钥），与元数据库一起留存。
