# v2.4.0 数据迁移向导（灰度实测）

> 镜像标签：`custos-server:v2.4.0`
> 版本号唯一来源：`.env` 的 `VERSION=v2.4.0`（`scripts/deploy.sh` / `Makefile` / `docker compose` / 应用内 `config.APP_VERSION` 均从此读取）

---

## 一、本期主线

新增「**数据迁移向导**」：在真实旧数据上把库从源端搬到目标端，覆盖两类最具代表性的场景：

- **MariaDB → MariaDB**（同引擎）：可桥接（bridge）做增量追平，管道 `continuous`。
- **MySQL 5.7 → MariaDB 12.3.3**（跨产品线）：自动落进「宽松桶」，管道 `stopcopy`（停写拷贝，无增量追平）。

设计上**不拆两套独立体系**，而是用「能力标志」驱动同一套骨架：MySQL 5.7 因天然躲开 `caching_sha2` 与 `utf8mb4_0900_ai_ci` 两个必炸项，自动与 MariaDB 落进同一「宽松桶」，无需硬编码例外；MySQL 8.0+ → MariaDB 按决策明确拒绝。

---

## 二、核心设计

### 1. 能力矩阵 `capabilities()` 为门禁唯一真源
```
same_engine = (src_flavor == tgt_flavor)
physical    = same_engine                 # 跨引擎物理迁移不可行(MySQL8 删 .frm)
bridge      = same_engine and 两端皆 mariadb   # 跨引擎 GTID 格式不通
pipeline    = "continuous" if (同引擎且目标 mariadb) else "stopcopy"
refused     = 跨引擎 and src 为 MySQL 且 major>=8
```
| 组合 | same_engine | physical | bridge | pipeline | refused |
|---|---|---|---|---|---|
| MariaDB → MariaDB | ✅ | ✅ | ✅ | continuous | ❌ |
| MySQL 5.7 → MariaDB | ❌ | ❌ | ❌ | stopcopy | ❌ |
| MySQL 8.0 → MariaDB | ❌ | ❌ | ❌ | stopcopy | ✅（暂不实现） |

### 2. 引擎方言适配层
- `tool_dialect`：用 `<binary> --help` 探测真实方言（Debian 的 `mysql-client` 仅是指向 `mariadb-client` 的过渡包，按文件名判断会误判）。
- `dump_gtid_args` / `ssl_args`：按源端方言分流 dump 工具与参数、TLS 校验开关。

### 3. 迁移前兼容性预检（dry-run）
两层检查（只读 `information_schema` + 仅结构 `--no-data` 改名落目标 scratch schema 真实导入再删除）：
- 元数据层：排序规则 / 存储引擎 / JSON 列 / `WITH PARSER` 全文解析器
- 结构试运行：抓 `information_schema` 看不出的 DDL 失败

**实测效果**：对含 `risky`(ngram) 库的 MySQL 5.7 源，在真实迁移开始前报出 2 个阻断项，而非等到 TB 级拷贝一半才失败。

### 4. 后台异步逐步执行
seed / bridge / verify / cutover / cleanup：进度 / 阶段文字 / 实时日志落库，前端 1.5s 轮询 `/status`（同步 `run_step` 会让请求超时，前端永远看不到进度）。

## 三、修复的必炸点（全部由真实环境坐实）

| # | 问题 | 现象 | 修复 |
|---|---|---|---|
| 1 | dump 工具参数互斥 | `mariadb-dump --set-gtid-purged=ON` → `unknown variable`；`mysqldump --gtid` → `unknown option` | 按源端产品线分流工具与 GTID 参数（`dump_gtid_args`） |
| 2 | 探测变量名错误 | `SELECT @@log_replica_updates` 在 MariaDB 12.3.3 → `ERROR 1193` | 改 `@@log_slave_updates`，逐项探测不拖垮整体 |
| 3 | 管理器镜像无数据库客户端 | 纯 `python:3.11-slim`，无 `mysqldump/mariadb-dump`，逻辑/物理通道整体跑不起来 | Dockerfile 增加 `mariadb-client` |
| 4 | GTID 位点写进 dump | `SET GLOBAL gtid_slave_pos=''` 与目标 binlog 冲突 → `ERROR 1948` | 位点改为快照，留给 bridge 阶段 |
| 5 | 方言按文件名判断误判 | Debian 的 `mysql-client` 是指向 `mariadb-client` 的过渡包，传 `--set-gtid-purged` 直接失败 | 改用 `<binary> --help` 探测真实方言（`tool_dialect`） |
| 6 | 自签名证书 TLS 失败 | MySQL 5.7 自签证书 + 新客户端默认校验 → `TLS/SSL error 2026` | 对 MariaDB 方言加 `--ssl-verify-server-cert=0` |
| 7 | subprocess stdin 二次 flush | 手动 close(stdin) 后再 `communicate()` → `ValueError: flush of closed file` | 置 `stdin=None` 后 communicate |

## 四、实测结论

- **MariaDB → MariaDB**（真实 1GB 旧数据）：certd 47表/396行、sunpanel 8表/117行，**源=目标**，23s。
- **MySQL 5.7.44 → MariaDB 12.3.3**：shop 2表/6行一致；自动判定 `cross_engine=True / pipeline=stopcopy / bridge=False`。
- **预检拦截 ngram 全文索引**：提前拦下 2 个阻断项，不搬数据。
- **后台异步进度链路**：进度 0%→45%、阶段文字、带时间戳日志均正确落库。

---

## 五、已知边界（诚实清单）

- `bridge / verify / cutover / cleanup` 四步尚未跑端到端（仅 `seed` 与预检已实测）。
- 物理通道未实测（镜像内还缺 `mariabackup`；且物理跨引擎本就被门禁拒绝）。
- 账号/权限迁移未实现（当前排除 `mysql` 系统库，跨引擎时为必做项）。
- MySQL 8.0 → MariaDB 按用户决策暂不实现（`refused=True`）。

---

## 六、升级方式

1. 拉取新代码（`.env` 已含 `VERSION=v2.4.0`）。
2. 重建并重启管理器（版本号经环境变量注入容器，必须重建镜像才生效）：
   ```bash
   ./scripts/deploy.sh up -d --build
   ```
3. 节点侧无需升级（迁移是管理器端能力，不影响被管节点的高可用逻辑）。
