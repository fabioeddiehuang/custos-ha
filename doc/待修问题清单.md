## UI-001 数据迁移页：全站页脚错位到主区右侧（垂直居中）

- **状态**：已修（2026-09-17 统一批次）
- **发现日期**：2026-09-17
- **现象**：在「数据迁移向导」页（`/migration`），页面右下应位于底部的全站页脚「Custos — Never let your database down」，跑到了**主内容区右侧、纵向约居中**的位置，像是浮在半空的一列文字（截图已划红圈）。
- **影响面**：仅视觉错位，不影响功能；但页面观感割裂明显，其它页面待确认是否同样复现。
- **位置（已定位）**：
  - 出错页面模板：`app/templates/migration.html`
  - 罪魁：**第 104 行多了一个 `</div>`**（`<div class="card" id="step2">` 提前闭合）。
  - 受影响方：全站页脚 `app/templates/base.html:126`（`.site-foot`）。
- **根因（已核实）**：
  1. `migration.html` 里 `<div` 共 70 个、`</div>` 共 71 个——**闭合标签多 1 个**。
  2. 多出的 `</div>`（第 104 行）把 `#step2` 卡片提前闭合，使「迁移通道 / 迁移任务名称 / 创建按钮」（第 106–120 行）溢出到卡片外。

  4. 作为横向 flex 子项，页脚被拉到主区右侧并纵向拉伸，文字垂直居中——与截图现象一致。
  - 相关布局：`app/static/v3.css:48`（`.app{display:flex}`）、`v3.css:68`（`.main{display:flex;flex-direction:column}`）、`base.html:56-63`（`.site-foot` 样式）。
- **建议修复**：删除 `migration.html` **第 104 行**多余的 `</div>`，使 `#step2` 卡片在「创建迁移任务并继续」按钮后（第 121 行）正常闭合。改完重数一遍 `<div>/</div>` 应为 70/70（或前后一致）。
- **附带收益**：修复后「迁移通道」选择区与「迁移任务名称/创建按钮」会重新回到第 2 步卡片内部，层级与视觉更合理。

## BUG-001 迁移 cutover 在多节点目标场景下只登记 203，会把新主“拽出”原集群（重大）

- **状态**：已修（2026-09-17 统一批次）
- **发现日期**：2026-09-17
- **现象（用户实测）**：执行「停桥切换 / 收尾回收」后，新主 203 从原 3 节点集群（203/213/33）里消失/被移出，疑似被程序移除出集群。
- **位置（已对照代码定位）**：
  - `app/migration.py:902` `cleanup()`：**只连源库 177** 执行 `DROP USER replication@'%'` + `SET GLOBAL read_only=ON`，**根本不碰 203**。所谓“收尾回收把 203 移出集群”并非 cleanup 所为。
  - `app/migration.py:904` `cutover()` 调 `create_cluster()` 新建一个 Custos 集群；`:913` `_register_target_node(cluster_id, tgt_host=203, …)` 把 **仅 203 一个节点**登记进该新集群，且用 `ON DUPLICATE KEY UPDATE cluster_id=<新id>`（`:887-888`）覆盖 203 原有集群归属。
- **根因**：迁移模块假设“目标是单节点、要被初始化成一个全新集群”，**没有处理“目标本身已是多节点集群”的情况**：
  1. `cutover` 新建集群并只登记 `tgt_host`（203），**不登记 213/33**；
  2. 若 203 此前已在某集群，`_register_target_node` 的 `ON DUPLICATE KEY UPDATE cluster_id` 会把 203 的归属改到新建的单节点集群 → 表现为“203 被拽出原集群”。
- **建议修复**：目标若已是 Custos 集群，应**复用已有集群**而非 `create_cluster` 新建；且须把目标整集群节点（203/213/33）一并登记，不能只认 203。需在 cutover 前判断目标是否已在集群中。
- **关联讨论**：见 DESIGN-001（收尾/桥接职责）。

## DESIGN-001 收尾回收 / 桥接 / 种子的“闭环时机”需重新梳理（讨论中）

- **状态**：讨论中（a 点“177/203 混淆”已随 BUG-001 修复缓解；b/c“是否仍需收尾回收”仍待产品决策）
- **发现日期**：2026-09-17
- **背景（用户观点）**：
  - a. 老主 177:3306 与新主 203 是两套库，不应混淆；当前代码 cleanup 作用于 `src`(177)、cutover 作用于 `tgt`(203)，分工正确，但“只登记 203、新建集群”把多节点关系搞乱（见 BUG-001）。
  - b. 逻辑通道的“数据种子”一旦同步成功，新集群 3 节点（203/213/33）已拿到数据，VIP 理论上即可接管旧主；故认为种子即“闭环”。
  - c. 介于 a/b，认为“收尾回收”这一步没有必要。
- **技术评估（待拍板）**：
  - 种子是**一次性**拷贝；在“种子完成 → VIP 真正切换”之间，旧主 177 若仍在线接收写入，这些增量数据不会进新集群——**桥接（177→203 复制）正是覆盖这段追赶窗口**，保证切换瞬间近零丢失。
  - 因此：若切换前先把旧主 177 **置只读（冻结写）**，则种子确实足够、桥接可省；若要求旧主在线（零停机迁移），桥接不可省。
  - “收尾回收”建议**保留**为回退安全网：切换后留 177 只读暖备一段时间，万一新集群异常可回切；但不应在收尾阶段动 203 的集群归属（同 BUG-001）。
- **待决策**：是否区分“冻结式迁移（可省桥接）”与“在线迁移（需桥接）”两种模式；以及暖备保留期是否可配置。

## BUG-002 203 被拽出后独立成集群，原从节点 213/33 仍是其从库却无法接管（元数据/拓扑分裂）

- **状态**：已修（随 BUG-001 一并修复）
- **发现日期**：2026-09-17
- **现象（用户实测）**：203 被移出新集群、自己成了新建单节点集群的主库；而 213、33 在 Custos 元数据里已脱离 203，但物理上**仍是 203 的从库且均 read only**，手动“设为主库”报 `设置失败(确认节点在线且已配置账号)`。用户困惑：203 都去了新集群，213/33 怎么还是它的从库。
- **根因**：与 BUG-001 同源——`cutover` 把 203 写入新建单节点集群、`_register_target_node` 只登记 203，213/33 未登记。结果 **Custos 元数据（集群归属）与真实 MySQL 复制拓扑（213/33 → 203）不一致**：monitor 认为 213/33 无主/孤立故不可提升，而它们实际还在跟 203 复制。
- **建议修复（与 BUG-001 一并）**：目标若是多节点集群，cutover 须把 203/213/33 **整体登记进同一集群**，保持元数据与真实拓扑一致；孤立从节点才可正常接管/提升。

## BUG-003 目标形态选“裸机 MariaDB”，节点管理里 203 却显示“容器”（待核实）

- **状态**：已修（2026-09-17 统一批次；用户仍需复测裸机选择是否生效）
- **发现日期**：2026-09-17
- **现象**：迁移目标节点形态勾选“裸机 MariaDB”，但节点管理中 203 的标签为“容器”。
- **根因（已定位，数据层确定）**：
  - 落库值确实是 `mariadb-docker`：`app/templates/nodes.html:118` `{% elif n.node_type == 'mariadb-docker' %}…MariaDB 容器…` 据此渲染“容器”标签。
  - 创建端点兜底：`app/api.py:2796` `api_migration_create` 用 `"node_type": b.get("node_type", "mariadb-docker")`——若请求体未带 truthy 的 `node_type`，即静默回退为 `mariadb-docker`。
  - 存储链路完整：`save_task`（`migration.py:82`）把整个 `config`（含 `node_type`）加密落库，`get_task`（`:100`）+ `cutover`（`:913`）回读 `cfg.get("node_type", "mariadb-docker")`——只要创建时存的是 `mariadb` 就会正确显示裸机；现落库为 `mariadb-docker`，说明**创建请求没带上“裸机”值**。
  - 表单默认选中即容器：`migration.html:90` `<option value="mariadb-docker" selected>` 默认选中「容器化 MariaDB」；`:232` 确实把 `$("tgtType").value` 放进请求体。
- **待用户确认（关键）**：表单已把 `node_type` 发送、创建端点也读取了，但最终落库为容器，唯一解释是**创建请求里的 `node_type` 值是 `mariadb-docker`**。请确认第二步你是否真的把下拉从默认的「容器化 MariaDB」改成了「裸机 MariaDB」——若没改，落库自然是容器（非代码 bug）；若确实改了却仍落库容器，则前端 payload 漏传了选中值（需查 `saveTask` 组装）。两种都可能，需你核实操作。
- **用户回应（2026-09-17）**：后续自行观察确认，暂不定论；若复现仍异常再走“前端漏传”排查。
- **建议修复（无论哪种）**：① 下拉默认不要 `selected` 容器，或创建端点对缺失 `node_type` 直接报错而非静默回退；② 若确认前端漏传，修正 `saveTask` 组装；③ 展示层与表单选项口径一致。
