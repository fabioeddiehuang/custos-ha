## 通用根因铁律：UI / 页面变形头号元凶 = 模板 `<div>` 开闭不平衡

> **结论（多次实战验证，含 2026-09-24 UI-001 复发）**：页面布局 / UI 变形，**十有八九是模板里 `<div>` 开闭标签不平衡**——
> 多一个 `</div>` 会提前闭合容器，把后续元素（典型是全站页脚 `.site-foot`）挤出原本的 flex 父级，
> 变成横向 flex（`.app{display:flex}`）的直系子项 → 页脚被甩到**页面最右侧、纵向居中**，像浮在半空的一列文字。
> 同源症状还有：卡片内容溢出到卡片外、步进条 / 栅格错位、弹窗跑偏、字段被压成一行。
>
> **易发场景**：大段增删结构（如 2.4.0 重做删旧 step4/5、改 `form-grid` 为单字段）时最容易多删 / 多留一个 `</div>`；
> 复制粘贴整块时首尾标签没对齐；JS 模板串（如 `updateGuide` 里的 `'<div ...>'`）里的标签容易让人误判真实标签数——
> **校验必须剥离 `<script>` / `<style>` 再数**，否则 `grep` 的计数会被 JS 字符串污染（见下自检脚本）。
>
> **自检铁律（每次改完任意 `.html` 模板必跑）**：用标准库 `html.parser`（自动把 `<script>/<style>` 当纯文本、不解析其中标签）解析，
> 出现 `stray </div>` 即定位到那一行删掉；`open` 栈非空即有未闭合标签需补。命令：
> ```bash
> python3 - <<'PY'
> from html.parser import HTMLParser
> VOID={'area','base','br','col','embed','hr','img','input','link','meta','param','source','track','wbr'}
> class P(HTMLParser):
>     def __init__(s): super().__init__(convert_charrefs=True); s.stack=[]; s.err=[]
>     def handle_starttag(s,t,a):
>         if t in VOID: return
>         s.stack.append((t,s.getpos()[0]))
>     def handle_endtag(s,t):
>         if t in VOID: return
>         for i in range(len(s.stack)-1,-1,-1):
>             if s.stack[i][0]==t:
>                 del s.stack[i:]; return
>         s.err.append(("stray </%s>"%t,t,s.getpos()[0]))
> p=P(); p.feed(open('app/templates/<文件>.html',encoding='utf-8').read())
> print("open:",p.stack,"err:",p.err,"=>","BALANCED" if not p.stack and not p.err else "BROKEN")
> PY
> ```
> 实测：2026-09-24 删 step1 末尾多余 `</div>` 后，该脚本输出 `open: [] err: [] => BALANCED`，页脚即归位页面底部。

## UI-001 数据迁移页：全站页脚错位到主区右侧（垂直居中）

- **状态**：已修（2026-09-17 统一批次；**2026-09-24 复发并二次修复**——2.4.0 纯逻辑重做删旧 step4/5 时又遗留一个多余 `</div>`，页脚再次甩到页面最右侧，已删 step1 卡片末尾多余闭合标签修复）
- **发现日期**：2026-09-17
- **现象**：在「数据迁移向导」页（`/migration`），页面右下应位于底部的全站页脚「Custos — Never let your database down」，跑到了**主内容区右侧、纵向约居中**的位置，像是浮在半空的一列文字（截图已划红圈）。
- **影响面**：仅视觉错位，不影响功能；但页面观感割裂明显，其它页面待确认是否同样复现。
- **位置（已定位）**：
  - 出错页面模板：`app/templates/migration.html`
  - 罪魁：**第 104 行多了一个 `</div>`**（`<div class="card" id="step2">` 提前闭合）。
  - 受影响方：全站页脚 `app/templates/base.html:126`（`.site-foot`）。
- **根因（已核实）**：
  1. `migration.html` 里 `<div` 共 70 个、`</div>` 共 71 个——**闭合标签多 1 个**。
  2. 多出的 `</div>`（第 104 行）把 `#step2` 卡片提前闭合，使「迁移通道 / 迁移任务名称 / 创建按钮」（第 106–120 行）溢出到卡片外。
  3. 这个多余的闭合标签在 `base.html` 的层级里继续“错配”，把全站页脚 `.site-foot` 挤出了 `.main`，变成 `.app`（`display:flex`，方向为横向 row）的直系子元素。
  4. 作为横向 flex 子项，页脚被拉到主区右侧并纵向拉伸，文字垂直居中——与截图现象一致。
  - 相关布局：`app/static/v3.css:48`（`.app{display:flex}`）、`v3.css:68`（`.main{display:flex;flex-direction:column}`）、`base.html:56-63`（`.site-foot` 样式）。
- **建议修复**：删除 `migration.html` **第 104 行**多余的 `</div>`，使 `#step2` 卡片在「创建迁移任务并继续」按钮后（第 121 行）正常闭合。改完重数一遍 `<div>/</div>` 应为 70/70（或前后一致）。
- **附带收益**：修复后「迁移通道」选择区与「迁移任务名称/创建按钮」会重新回到第 2 步卡片内部，层级与视觉更合理。

## BUG-001 迁移 cutover 在多节点目标场景下只登记 203，会把新主“拽出”原集群（重大）

- **状态**：已修（2026-09-17 统一批次）
- **发现日期**：2026-09-17
- **现象（用户实测）**：执行「停桥切换 / 收尾回收」后，新主 203 从原 3 节点集群（203/213/33）里消失/被移出，疑似被程序移除出集群。
- **位置（已对照代码定位）**：
  - `app/migration.py:902` `cleanup()`：**只连源库 177** 执行 `DROP USER replication@'%'` + `SET GLOBAL read_only=ON`，**根本不碰 203**。所谓“收尾回收把 203 移出集群”并非 cleanup 所为。
  - `app/migration.py:904` `cutover()` 调 `create_cluster()` 新建一个 Custos 集群；`:913` `_register_target_node(cluster_id, tgt_host=203, …)` 把 **仅 203 一个节点**登记进该新集群，且用 `ON DUPLICATE KEY UPDATE cluster_id=<新id>`（`:887-888`）覆盖 203 原有集群归属。
- **根因**：迁移模块假设“目标是单节点、要被初始化成一个全新集群”，**没有处理“目标本身已是多节点集群”的情况**：
  1. `cutover` 新建集群并只登记 `tgt_host`（203），**不登记 213/33**；
  2. 若 203 此前已在某集群，`_register_target_node` 的 `ON DUPLICATE KEY UPDATE cluster_id` 会把 203 的归属改到新建的单节点集群 → 表现为“203 被拽出原集群”。
- **建议修复**：目标若已是 Custos 集群，应**复用已有集群**而非 `create_cluster` 新建；且须把目标整集群节点（203/213/33）一并登记，不能只认 203。需在 cutover 前判断目标是否已在集群中。
- **关联讨论**：见 DESIGN-001（收尾/桥接职责）。

## DESIGN-001 收尾回收 / 桥接 / 种子的“闭环时机”需重新梳理（讨论中）

- **状态**：讨论中（a 点“177/203 混淆”已随 BUG-001 修复缓解；b/c“是否仍需收尾回收”仍待产品决策）
- **发现日期**：2026-09-17
- **背景（用户观点）**：
  - a. 老主 177:3306 与新主 203 是两套库，不应混淆；当前代码 cleanup 作用于 `src`(177)、cutover 作用于 `tgt`(203)，分工正确，但“只登记 203、新建集群”把多节点关系搞乱（见 BUG-001）。
  - b. 逻辑通道的“数据种子”一旦同步成功，新集群 3 节点（203/213/33）已拿到数据，VIP 理论上即可接管旧主；故认为种子即“闭环”。
  - c. 介于 a/b，认为“收尾回收”这一步没有必要。
- **技术评估（待拍板）**：
  - 种子是**一次性**拷贝；在“种子完成 → VIP 真正切换”之间，旧主 177 若仍在线接收写入，这些增量数据不会进新集群——**桥接（177→203 复制）正是覆盖这段追赶窗口**，保证切换瞬间近零丢失。
  - 因此：若切换前先把旧主 177 **置只读（冻结写）**，则种子确实足够、桥接可省；若要求旧主在线（零停机迁移），桥接不可省。
  - “收尾回收”建议**保留**为回退安全网：切换后留 177 只读暖备一段时间，万一新集群异常可回切；但不应在收尾阶段动 203 的集群归属（同 BUG-001）。
- **待决策**：是否区分“冻结式迁移（可省桥接）”与“在线迁移（需桥接）”两种模式；以及暖备保留期是否可配置。

## BUG-002 203 被拽出后独立成集群，原从节点 213/33 仍是其从库却无法接管（元数据/拓扑分裂）

- **状态**：已修（随 BUG-001 一并修复）
- **发现日期**：2026-09-17
- **现象（用户实测）**：203 被移出新集群、自己成了新建单节点集群的主库；而 213、33 在 Custos 元数据里已脱离 203，但物理上**仍是 203 的从库且均 read only**，手动“设为主库”报 `设置失败(确认节点在线且已配置账号)`。用户困惑：203 都去了新集群，213/33 怎么还是它的从库。
- **根因**：与 BUG-001 同源——`cutover` 把 203 写入新建单节点集群、`_register_target_node` 只登记 203，213/33 未登记。结果 **Custos 元数据（集群归属）与真实 MySQL 复制拓扑（213/33 → 203）不一致**：monitor 认为 213/33 无主/孤立故不可提升，而它们实际还在跟 203 复制。
- **建议修复（与 BUG-001 一并）**：目标若是多节点集群，cutover 须把 203/213/33 **整体登记进同一集群**，保持元数据与真实拓扑一致；孤立从节点才可正常接管/提升。

## BUG-003 目标形态选“裸机 MariaDB”，节点管理里 203 却显示“容器”（待核实）

- **状态**：已修（2026-09-17 统一批次；用户仍需复测裸机选择是否生效）
- **发现日期**：2026-09-17
- **现象**：迁移目标节点形态勾选“裸机 MariaDB”，但节点管理中 203 的标签为“容器”。
- **根因（已定位，数据层确定）**：
  - 落库值确实是 `mariadb-docker`：`app/templates/nodes.html:118` `{% elif n.node_type == 'mariadb-docker' %}…MariaDB 容器…` 据此渲染“容器”标签。
  - 创建端点兜底：`app/api.py:2796` `api_migration_create` 用 `"node_type": b.get("node_type", "mariadb-docker")`——若请求体未带 truthy 的 `node_type`，即静默回退为 `mariadb-docker`。
  - 存储链路完整：`save_task`（`migration.py:82`）把整个 `config`（含 `node_type`）加密落库，`get_task`（`:100`）+ `cutover`（`:913`）回读 `cfg.get("node_type", "mariadb-docker")`——只要创建时存的是 `mariadb` 就会正确显示裸机；现落库为 `mariadb-docker`，说明**创建请求没带上“裸机”值**。
  - 表单默认选中即容器：`migration.html:90` `<option value="mariadb-docker" selected>` 默认选中「容器化 MariaDB」；`:232` 确实把 `$("tgtType").value` 放进请求体。
- **待用户确认（关键）**：表单已把 `node_type` 发送、创建端点也读取了，但最终落库为容器，唯一解释是**创建请求里的 `node_type` 值是 `mariadb-docker`**。请确认第二步你是否真的把下拉从默认的「容器化 MariaDB」改成了「裸机 MariaDB」——若没改，落库自然是容器（非代码 bug）；若确实改了却仍落库容器，则前端 payload 漏传了选中值（需查 `saveTask` 组装）。两种都可能，需你核实操作。
- **用户回应（2026-09-17）**：后续自行观察确认，暂不定论；若复现仍异常再走“前端漏传”排查。
- **建议修复（无论哪种）**：① 下拉默认不要 `selected` 容器，或创建端点对缺失 `node_type` 直接报错而非静默回退；② 若确认前端漏传，修正 `saveTask` 组装；③ 展示层与表单选项口径一致。

  - P3（2026-09-20 根治「还是报没容器」）：**把 SSH 失败 / docker 缺失 与 真的没容器 区分开**。`_find_mariadb_container` 现返回 `(cid, diag)`，diag ∈ {ok/ssh_fail/docker_missing/no_container}；并在远端先 `echo DOCKER_OK/DOCKER_NO` 探 docker 可用性、再用 `docker ps --format '{{.ID}}|{{.Names}}|{{.Image}}'` 取全部运行容器、按 **容器名或镜像含 mariadb** 选取（不依赖精确名 `custos-mariadb` / compose 路径 / 发布端口）。根因澄清：向导「兼容性预检」是 **MySQL 直连**（host:port:user:pass），与「SSH 跑 docker ps」是两套通道/凭证——MySQL 通 ≠ SSH 通，故需分别校验；源端 SSH 走向导「源机 SSH 账号/密码」(src_ssh_user/src_ssh_pass)，目标端走管理器 root 密钥。报错信息现在会精确指明是「SSH 不可达」「docker 不可用」还是「真的无 MariaDB 容器」。

## UX-010 停写迁移模式下的「停写检测」工具

- **状态**：已废弃（2.4.0 纯逻辑重做：停写/桥接模式已取消，/api/migration/{id}/freeze_check 端点已移除）
- **背景**：源库未开 binlog ⇒ 无桥接可追平，数据种子（一次性快照）是唯一数据来源，种子之后的源库写入会永久丢失。因此"源库是否已停写"必须能被**实测验证**，而不是只靠用户口头确认。
- **实现**：
  - 后端 `migration.check_write_freeze(task)`：连源库间隔 `FREEZE_SAMPLE_SEC=3` 秒采样两次写入类计数器（`Com_insert/update/delete/replace/commit` + `Innodb_rows_inserted/updated/deleted`）取差值，并读取 `@@read_only` / `@@super_read_only`。
  - 端点 `POST /api/migration/{task_id}/freeze_check`（同步端点，FastAPI 放线程池，不阻塞事件循环）。
  - 前端：停写模式下第四步显示「🔍 停写检测」按钮（桥接模式则显示「追平检测」），结果展示 DML 次数 / 行变更 / 只读状态 / 明细。
- **安全设计（勿简化）**：
  1. 检测只提供判断依据，**不自动放行切换**——最终仍需勾选「源库已停写」并过危险确认。
  2. **计数器回退保护**：若出现负值（被 `FLUSH STATUS` 重置），判为 `unreliable=True` 且**绝不置 frozen**。因为按 0 处理会**误判为已停写**（漏报），比误报危险得多——会让用户在仍有写入时切换。
- **测试**（mock，三场景全过）：已停写→frozen/0/0；仍在写入→不 frozen、writes=27、rows=23；计数器重置→unreliable=True 不 frozen。

## UX-011 源库未开 binlog 时，用 root 自动生成「开启 binlog」可执行方案

- **状态**：已废弃（2.4.0 纯逻辑重做：binlog/桥接需求已取消，/api/migration/plan_binlog 端点已移除）
- **用户质疑**："既然第一步给了 root 权限，为什么不用 root 直接开启源库的 binlog？"
- **结论（重要，勿再提自动开启）**：
  1. `log_bin` 是**静态变量**，MySQL/MariaDB 均不支持 `SET GLOBAL log_bin=ON` 在线开启，**必须改配置文件并重启 mysqld 进程**。
  2. 向导拿到的是**数据库 root**（只能执行 SQL），**改不了 my.cnf**（文件系统）、**重启不了 mysqld**（进程管理）——除非另给源机的 SSH 凭据（表单从未收集）。
  3. 即便有 SSH 也**绝不能自动执行**：改生产库配置 + 重启会造成业务中断，且 binlog 路径/格式/过期清理/磁盘规划均需人工决策。
- **实现（把 root 用在刀刃上）**：`plan_binlog_enable(cfg)` 用已有 root 连接探测 `VERSION()` / `@@datadir` / `@@server_id` / `@@log_bin` / `SHOW SLAVE HOSTS` / `SHOW REPLICA STATUS`，自动生成：
  - 可直接粘贴的 my.cnf 片段（server_id 建议值、按 datadir 推算的 log_bin 路径、binlog_format=ROW、expire_logs_days）
  - 若源库自身是别人的从库或挂着从库 ⇒ 自动追加 `log_slave_updates = ON`
  - 配置文件候选路径 + 五步操作步骤
  - 端点 `POST /api/migration/plan_binlog`；前端第一步停写模式下自动展示。
- **测试**：两场景通过（未开 binlog+server_id=0 → 建议 1001、生成片段；源库本身是从库 → 自动追加 log_slave_updates）。

## BUG-005 接管（adopt）引导在目标库端口已占用时失败（端口 3307 实战）

- **状态**：已修（v2.5.0 接管批次）
- **发现日期**：2026-09-30
- **现象**：把一台已在跑 MariaDB（端口 3307）的单机节点 177 接管进集群，在节点执行 curl 引导命令后报
  `[error] 端口 3307 已被占用（ss -ltn 可见），请释放后重试`，流程卡死。部分旧构建还会跑
  `Install-ha-mariadb-Node.sh` 全量装库（等于重装数据库），与「接管＝纳管不是重建」铁律冲突。
- **位置（已定位）**：
  - `app/bootstrap.py` `render_bootstrap_script` 的环境预检：端口占用块对**整个 compose** 做扫描，
    会命中被接管库本身就在用的端口（如 3307），且旧版 `node_install_cmds` 在接管路径仍注入 DB 安装脚本。
  - `app/adopt.py` `register_and_bootstrap` 已传 `sidecar_only=True`（只装 keepalived + agent）。
- **根因**：接管 sidecar_only 模式不碰已有数据库，被接管库端口被占用是【预期】而非冲突；
  预检却把它当新装库的端口冲突 `die` 掉。
- **建议修复（已做）**：
  1. `bootstrap.py` 端口预检块包进 `if [ -n "$SIDECAR_ONLY" ]` 守卫，接管场景直接跳过端口预检；
     `render_bootstrap_script` 注入 `SIDECAR_ONLY` 占位符并按 `sidecar_only` 填 "1"/""。
  2. `node_install_cmds` 已确认仅 `docker compose up -d keepalived custos-node-agent`，绝不跑 Install 脚本。

## BUG-006 接管允许「单机实例」接入已有节点的集群，导致监控误判复制状态

- **状态**：已修（v2.5.0 接管批次）
- **发现日期**：2026-09-30
- **现象**：用户把单机 177 接管进已有主从集群「纳管测试」（含 213/203），执行后仪表盘显示
  `192.168.1.177:3307 slave ● 复制正常← 192.168.1.213:3307`——177 本应是独立单机，却立刻被显示为 213 的从库。
- **位置（已定位）**：`app/api.py` `api_adopt_run` 未校验目标集群是否已有节点；`app/adopt.py`
  `register_and_bootstrap` 用 `probe.master`（单机时等于节点自身）把 177 标成 `role="master"`，
  与集群已有主库 213 撞角色，monitor 遂自动把 177 重指为 213 的从库，产生**错误复制通道**。
- **根因**：接管＝纳管外部已有库，应为「新建集群」或「空集群」；把节点塞进已有节点的集群违反
  DESIGN-006（单机须纳管为独立集群），且会引发数据不一致与监控误判。
- **建议修复（已做）**：`api_adopt_run` 探测后增加校验——若目标 `cluster_id` 对应的集群已含节点，
  直接拒绝并提示「选＋新建集群纳管为独立集群」。
- **关联**：DESIGN-006（原主 177 纳管为独立集群）；接管功能测试清单「重点验证点 3（sidecar 只装不重装）」。
