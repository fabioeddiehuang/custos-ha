# 集群接管（adopt）功能测试流程

> 日期：2026-09-29
> 版本：Custos-HA v2.5.0（F10 集群接管）
> 目的：在真实环境验证接管功能的可用性；同时顺带验证 DESIGN-005（同机多实例纳管）与 DESIGN-006（迁移后原主 177 纳管为独立集群）的可行路径。
> 配套设计：`doc/开发/v2.4.1-接管设计.md`；实现：`app/adopt.py` + `app/templates/adopt.html`。

---

## 0. 功能边界（测试前必读）

- **接管 = 纳管，不是重建**：老库正在跑业务，向导不碰数据、不重装数据库、不在阶段 1 改动复制拓扑。
- **三层架构**：
  - 阶段 0 `probe`：只读、幂等、可反复跑（探测版本 / server_id / binlog / GTID / 复制状态 / 数据量 / 权限，给出集群级结论）。
  - 阶段 1 `adopt`：建 Custos 接管账号 + 登记 nodes/hosts + 生成「一行引导命令」装 sidecar（keepalived + agent）。
  - 阶段 2 `extend`：**开 binlog（需重启）→ 节点本机导出 → 导入 → 建复制**，仅场景 2 需要。
- **当前实现范围（重要）**：`app/adopt.py` 目前**只实现了 probe + 阶段 1**（`probe_node` / `probe_cluster` / `adopt_node` / `adopt_cluster` / `register_and_bootstrap`）。`extend`（阶段 2）**尚未实现** → 场景 2（单机接管）接管后**仍为单机，不会自动加从库**。
- **UI 四步**：① 填节点 → ② 探测（只读） → ③ 接管参数 → ④ 执行接管。

---

## 1. 前置条件

- 已部署 Custos 管理器（含 agent 引导通道 / token 下发）。
- 待接管节点是**已运行**的 MariaDB / MySQL 实例，且已知 root 口令。
- **节点与 Custos 管理器同二层网络**（VIP 漂移靠 VRRP，跨网段不成立）。
- 节点 root 具备 `CREATE USER` / `GRANT OPTION` 权限（建接管账号用）。
- 节点主机可直连公网或内网源（装 sidecar 用一键引导命令）。

---

## 2. 测试场景

### 场景 A（主线，必测）—— 已有主从复制集群（scenario: existing_repl）
- 准备：2+ 节点已建立主从复制，IO/SQL 双 Yes。
- 预期探测结果：`scenario=existing_repl`，`verdict=ready`，`master` 识别正确，各节点 `role` 正确（master/slave）。
- 这是接管的主战场，接管后 monitor 应接管 HA（主库故障自动切换 + VIP 漂移）。

### 场景 B —— 单机实例（scenario: single）
- 准备：单节点，无复制。
- 预期：`scenario=single`，`master` 指向该节点。
- **观察点**：因 `extend` 未实现，接管后该集群**只有单节点、无复制**。记录：监控页是否把它当 master、是否提示"无复制保护"。

### 场景 C（边界 / 负向，挑 2~3 个测）
- C1 混引擎族（一台 MySQL + 一台 MariaDB）：预期 `family_mismatch` blocker。
- C2 版本不一致（如 10.11 + 11.4）：预期 `version_mismatch` blocker。
- C3 server_id 重复：预期 `server_id_dup` blocker（撞 id 会搞坏复制）。
- C4 跨网段（节点不在同一 VLAN）：预期 `not_same_l2` blocker。
- C5 节点不可达（填错 IP/端口/密码）：预期 `all_unreachable` 或单节点 `ok=False`。
- C6 不支持版本（如 MySQL 5.7，EOL）：界面应有提示（非 blocker 但需观察）。

---

## 3. 逐步操作（对照 UI）

1. **① 填节点**：进入「集群接管」页，逐行填 IP / 端口 / 用户 / 密码；多节点点「＋ 再加一个节点」。
2. **② 探测（只读）**：点「开始探测（只读）」。记录返回：
   - 结论（`verdict`：可以接管 / 需先整改 / 不支持接管）
   - 场景（`scenario_label`）
   - 同网段（`l2_ok`）
   - 各节点：可连接 / 版本 / server_id / 角色 / binlog
   - issues 列表（每条的级别 blocker/warn 与修复建议）
3. **③ 接管参数**：
   - 选「＋ 新建集群」→ 填集群名称、VIP（节点同网段空闲 IP）、VIP 端口（默认 3306）、节点 root 用户/密码；
   - 或选已有集群（下拉）。
4. **④ 执行接管**：点「执行接管」。记录返回的**集群 ID** 与**每个节点的引导命令**。

---

## 4. 节点侧收尾动作（关键，漏了等于没接管）

- 把步骤 4 得到的**每条「一行引导命令」**分别拿到对应节点主机，**以 root 执行**（装 keepalived + agent 两个 sidecar）。
- 命令含**一次性凭据**，TTL 24h，请勿外传、勿重复使用。
- 执行后回 Custos 确认：
  - 节点在线、agent 心跳正常；
  - keepalived / VIP 状态正常（VIP 是否漂到主库）；
  - monitor 是否已接管该集群 HA（观察自动切换是否可用）。

---

## 5. 重点验证点 / 已知疑点（务必反馈）

1. **UI 放行过宽（疑似 bug，重点）**：设计意图是"有阻断项时不放开下一步（避免带病接管）"，但 `adopt.html` 仅当 `verdict==='unsupported'` 时才隐藏第三步。`needs_change`（含版本不一致 / server_id 重复 / 跨网段等 blocker）仍会**放开「接管参数」步骤并允许执行接管**。
   - 请在场景 C2/C3/C4 中确认：出现 blocker 时，UI 是否仍能进入第三步并执行接管？若能，请记录现象（疑似与设计不一致）。
2. **场景 2 extend 未实现**：单机接管后是否真的只有单节点、无复制？监控页如何呈现？
3. **sidecar 只装不重装**：确认引导命令是 `sidecar_only`（只装 keepalived + agent），**没有重装数据库**（绝对不能跑 Install-ha-mariadb-Node.sh 那种重装脚本）。
4. **接管后 HA 是否生效**：场景 A 下手动杀掉主库进程，观察从库能否自动提主 + VIP 漂移到新主。
5. **探测只读性**：执行探测前后，确认老库的账号、复制拓扑、数据**零变化**（探测应纯只读）。
6. **同网段校验**：跨 VLAN 的两个节点，探测是否明确报 `not_same_l2` 并给出"VIP 方案不成立"的提示。

## 6. 与 DESIGN-005 / DESIGN-006 合并验证

- **DESIGN-006（原主 177 纳管为独立集群 mariadb-old）**：本决策的执行路径**就是一次「新建集群 + adopt 接管」**操作（VIP/VRID 需另行规划，不与 ha-mariadb 撞车）。
  - 请在测试中**专门走一遍"把一台独立实例接管成新集群"**，记录是否顺畅、是否需要额外手动步骤。若成功，即验证了 DESIGN-006 的路径可行性。
- **DESIGN-005（同机多实例纳管）**：若测试涉及"同一台物理机上的多个实例（不同端口）"分别接管，会撞 `nodes` 表 `ip VARCHAR(64) PRIMARY KEY`（当前一机只能一条节点记录）→ 预计登记失败。
  - 若今天的测试**包含**同机多实例场景，请记录具体报错，作为 DESIGN-005 工作量的佐证；
  - 若**不包含**，DESIGN-005 仍按原排期单独评估（不属于本次接管测试范围）。
