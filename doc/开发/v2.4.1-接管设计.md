# v2.4.1 存量集群接管（adopt）设计

> 基线：**v2.4.0**（master 已重建为 2.4.0 内容，见提交 `13a7606`）。
> 立场：接管 = **纳管**，不是重建。老库在跑业务，第一原则是别把它搞坏。

---

## 1. 目标场景

| 场景 | 现状 | 接管要做的事 | 是否动数据 |
|---|---|---|---|
| **场景 1** | 已有多节点主从复制 | 加 VIP + agent 做容灾，**保留原有复制拓扑** | 否 |
| **场景 2** | 只有 1 台，无复制 | 以它为**主库**，另加一台**同版本**节点做从库 | 是（导出/导入） |

版本范围（外界存量前 3 + 本产品主线，非混布、只做同版本集群）：

| 引擎 | 版本 | 级别 |
|---|---|---|
| MySQL | 5.7 / 8.0 / 8.4 | 兼容 / 支持 / 支持 |
| MariaDB | 10.6 / 10.11 / 11.4 | 兼容 / 兼容 / 支持 |
| MariaDB | 12.3 | **主线**（Custos 自建集群） |

MySQL 5.7 已 EOL（无安全更新），纳管时在界面明确提示。

---

## 2. 三阶段架构（职责单一）

```
阶段 0  probe   只读、幂等、可反复跑 → 能力/健康报告 + 结论
阶段 1  adopt   不动数据：建账号 + 登记 nodes/hosts + 装 agent + keepalived + VIP
阶段 2  extend  仅场景 2：开 binlog(需重启) → 节点本机导出 → 导入 → 建复制
```

**为什么探测必须独立且只读**：探测应当在用户还没决定接管时就能跑，跑坏了就是事故；
且探测结论要驱动 UI 显示"能不能接、差哪一步"，必须是结构化数据而不是日志。

---

## 3. 硬约束（探测阶段校验，不满足判 blocker）

1. **同集群必须同版本** —— 用户明确要求非混布；混引擎族（MySQL↔MariaDB）也禁止（GTID 机制根本不兼容）。
2. **server_id 非 0 且互不相同** —— 撞 id 会直接搞坏复制（因此 2.4.0 已加自定义 server_id + 全局冲突校验）。
3. **节点必须同二层网络** —— VIP 漂移靠 VRRP，**跨网段不成立**。这是最容易踩的坑：两台老库在不同机房/VLAN 时，
   VIP 方案根本无法工作，必须在探测阶段就拒绝，而不是"装完才发现漂不过去"。
4. **现有复制必须健康**（场景 1）—— IO/SQL 双 Yes，否则先修复制再接管。

---

## 4. 非 GTID 老集群的处理（关键决策）

### 现状（v2.4.0 的事实）

`change_replication_sql` 三个分支**全是 GTID 自动定位**，没有任何 file/pos 分支：

```
mysql8  → SOURCE_AUTO_POSITION=1
mariadb → MASTER_USE_GTID=slave_pos
old(5.7)→ MASTER_AUTO_POSITION=1
```

且 `make_slave_of` 对 MySQL 会检查 `@@gtid_mode=ON`，否则直接失败。
**即：现状下非 GTID 老集群根本挂不上复制。**

### 方案（三层，唯一能兼顾"不产生 bug"与"仍能容灾"）

| 层 | 做法 | 风险 |
|---|---|---|
| **纳管** | 绝对不碰复制：不执行 `CHANGE MASTER TO`、不改 `gtid_mode`、不改 `server_id` | **零**（根本不碰） |
| **切换** | 走显式 file/pos 路径，判据=「主库**确认不可写**（进程停/已 read_only，不是连不上）+ 从库 IO/SQL 双 Yes 且延迟 0」；提主瞬间在从库取 `SHOW MASTER STATUS`(File/Pos) **落库保存**；老主恢复后用该坐标回挂 | 中，靠判据兜住 |
| **GTID 升级** | 独立、显式触发、可预检可回滚，**不放进纳管默认路径** | 高，故摘出必经路径 |

**非 GTID 集群默认禁止自动切换。** GTID 下可用 `GTID_SUBSET` 判断从库是否含全部事务；
非 GTID 下没有这个判据，只能靠"主库停写 + 从库追平"，做不到就**宁可不切** ——
否则"主库假死但仍在写"会造成真正的**双写分叉**，这是最严重的后果。

**能力边界必须明示**：集群标记 `repl_mode=file_pos`，UI 写清"传统位点复制：自动切换受限，需人工确认"。
假装支持才是最容易出 bug 的地方。

## 5. 其他关键设计点

- **导出下沉到节点本机**：接管场景一律由 `custos-node-agent` 调用节点自带的
  `mysqldump` / `mariadb-dump` 导出，而不是从管理器连过去。这样绕开
  MariaDB 客户端连 MySQL 8.0（`caching_sha2_password`）的协议/认证不兼容，
  管理器也不必为每个版本准备一套客户端。
- **版本能力档案作为单一真源**（`app/version_profile.py`）：集中管理 flavour / GTID 方言 /
  提主权限 / 关 binlog 权限 / 认证插件 / dump 工具，杜绝散落的 `if version >= ...`。
  权限给的是**候选清单**，实际授予前必须用 `SHOW PRIVILEGES` 过滤（沿用 `mariadb_matrix` 原则）。
- **文件投递不走 sshpass/rsync**：改为节点侧带一次性 token 主动从管理器 HTTP 拉取。
  避免密码出现在命令行、避免依赖 sshpass/rsync、也支持 NAT/单向网络。
- **不新增 `takeover_tasks` 表**：复用 2.4.0 已有的 progress/stage 轮询契约，
  列名与 `migration_tasks` 对齐，前端组件直接复用。
- **sidecar 部署形态**：先做 **Docker**（keepalived + agent 容器），后续再做**可执行文件/systemd** 路径。

## 7. 下一步（按风险从低到高）

1. `make_slave_of` 支持 `repl_mode=file_pos`：非 GTID 时跳过 `gtid_mode=ON` 检查，
   改用位点挂载。**这是切主路径的改动，风险较高，需先评审再动。**
2. 阶段 1 `adopt` 实现：建账号（权限按 `version_profile` 候选 + SHOW PRIVILEGES 过滤）、
   登记 nodes/hosts、装 sidecar。
3. 阶段 2 `extend` 实现：开 binlog（重启，需停机窗口确认）+ 节点本机导出导入。
4. API 与页面：probe 接口（只读）、接管向导页。

## 8. 代码组织约定（2026-09-25）

- **一个功能一个文件**：每个业务功能独立模块、命名即功能（`adopt` / `switchover` / `backup` / `migration`…）。共享底座（`mysql_compat` / `version_profile` / `db` / `config` / `mariadb_matrix`）单列，不按功能拆。
- **拆分出的文件放进子文件夹**：原 `app/ha_client.py`（2922 行）已重构为包 `app/ha_client/`，按职责分子模块：
  - `connection.py` 底层连接 / 游标 / root 回退
  - `status.py` 节点状态读取（只读·可写 / 复制位点 / binlog 用量 / 提主）
  - `gtid.py` GTID 解析与复制修复（IO/SQL 异常、匿名事务、位点缺口自愈）
  - `credentials.py` HA 账号 / 权限探测、建立与校正（host 去 % 集合）
  - `local_state.py` 节点本地主库标记（`ha_local.local_master_flag`）
  - `replication.py` 复制搭建与切换核心（`make_slave_of` / 起停从库 / 提主 / VIP 守卫）
  - `_const.py` 模块级常量集中（含 `__all__`，下划线名可 `from ._const import *`）
  - `__init__.py` facade，对外 `from app.ha_client import X` 与原单文件等价
- 单文件 ≤ ~600 行且单一职责；依赖单向（功能模块 → 底座），防循环 import。
- **阶段 2 `extend` 开关框架（补充）**：不止 binlog。接管所需但 flavor 默认关的系统变量
  （`log_bin` / `gtid_domain_id` / `gtid_strict_mode` 等）一律做成**显式 opt-in 开关（带 restart 标记）**；
  `probe_node` 报告缺失项，向导提供开启选项。优先落地 MariaDB 10.11（权限模型与 11.4 一致）。
