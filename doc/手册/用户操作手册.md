# Custos HA · 用户操作手册

> 适用版本：**v2.2.20**（与 `.env` 的 `VERSION` 一致）
> 定位：一套**以 MySQL/MariaDB 原生主从复制为底座、VIP + keepalived 提供单点访问**的高可用管理平台。支持**单管理端多集群**统一纳管，覆盖容器化与裸机多种部署形态。

---

## 1. 总体架构与三种部署形态

```
                         ┌─────────────────────────────┐
   浏览器 ──HTTP──▶       │  Custos 管理端 (manager)     │
                         │  · Web UI / API / 决策器     │
                         │  · 独立管理库 (外部 MySQL)    │
                         └──────────┬──────────────────┘
                                    │  TCP 探活 + 复制/凭证自愈
            ┌───────────────────────┼───────────────────────┐
            ▼                       ▼                        ▼
      [节点 A]                [节点 B]                 [节点 C]
   主库(VIP 归属)           从库(复制)              从库(复制)
   keepalived + MySQL      keepalived + MySQL       keepalived + MySQL
            └──────── VRRP 同一 VIP，主库漂移 ────────┘
```

**三种节点形态**（`node_type` 取值，安装/部署入口不同，纳管逻辑一致）：

| `node_type` | 形态 | 部署入口 | 典型端口 | 镜像 / 软件 | 数据目录 |
|------|------|------|------|------|------|
| `docker` | 容器化 MySQL 8.0 | `Install-mysql-docker-Node.sh` + compose | 3307 | `mysql:8.0` | `/data/custos-ha/mysql8` |
| `mariadb-docker` | 容器化 MariaDB 12.3.x | **纯 compose**：`docker compose up -d` | 3306 | `mariadb:12.3.3`（Debian 构建），回退 `12.3.2` | `/data/custos-ha/mariadb12` |
| `mariadb` | 裸机 MariaDB 12.x | `sudo bash Install-ha-mariadb-Node.sh` | 3306 | 宿主机已装 MariaDB | 宿主原有目录 |

> **同集群须同「引擎族」**：两种 MariaDB 形态（`mariadb` 与 `mariadb-docker`）可混部（同为 MariaDB GTID）；**MySQL 与 MariaDB 禁止混部**。
> 管理端对三类节点统一用 TCP 探活；复制/切换/自愈逻辑按 `mysql_version` 选择 MySQL 8.0 或 MariaDB 的复制语法。

### 1.1 容器化 MariaDB（`mariadb-docker`）要点

- **v2.2.13 起改为纯 compose**：生成目录**不再包含安装脚本**，入口即 `docker compose up -d`（一次性拉起 `mariadb` + `keepalived` 双服务）。
- 仅保留 `Uninstall-mariadb-docker-Node.sh`（卸载）。
- **裸机包只适配裸机**：裸机（`mariadb`）节点生成目录**不再交付**容器回退脚本 `Install-mariadb-docker-Node.sh`（已从 `app/node_assets` 移除）。目标机装不上 tarball（如 glibc 过低）时，请**创建节点直接选 `mariadb-docker`**，可与裸机节点同集群混部（同为 MariaDB GTID）。
- **镜像选型**：统一用 **Debian 构建**的 `mariadb:12.3.3`；拉取失败或老 CPU 不兼容时回退 `mariadb:12.3.2`。
  - 已弃用 UBI 构建（`12.3.x-ubi`）：其默认 `USER=mysql(uid 999)` 易致宿主数据目录权限拒绝，且无 `/etc/mysql/my.cnf`（配置路径与 Debian 构建不一致）；同时不再要求 x86-64-v3 指令集，兼容 Anolis 7.9 等老 CPU。
- **VIP 端口在 compose 层映射**：业务连 `VIP:VIP_PORT` 直连容器，**不依赖节点 iptables/firewalld 转发**，规避 firewalld 与 ufw 差异。
- **低内存兼容**：`innodb_buffer_pool_size` 默认 512M（裸机/官方模板为 1G，2G 内存机易 OOM）。

## 2. 首次部署（管理端）

1. 准备一台管理机（建议 ≥2 核 4G），安装 Docker 与 docker compose v2。
2. 准备一个**独立的外部 MySQL/MariaDB** 作为管理库（与业务库隔离）。
3. 用 `scripts/deploy.sh` 启动管理端（首次启动自动建表 / 迁移）：

   ```bash
   cd custos-ha
   ./scripts/deploy.sh up -d          # 等价于 docker compose up -d --build（读取 .env 的 VERSION 后构建）
   ```

4. 浏览器访问 `http://<manager>:28888`，默认账号 `admin` / `admin`，**首次登录请修改密码**（设置 → 修改密码），并修改 `SECRET_KEY`/`WEB_PASS`。

> 镜像标签随版本：`custos:v2.2.16`（管理器）与 `custos-node:v2.2.16`（keepalived）。
> 改动 `./app` 下源码后**必须 `./scripts/deploy.sh up -d --build`** 重建，否则跑的仍是旧代码。

## 3. 创建集群（集群管理）

进入「集群管理」→ 新建集群，填写：

- **集群名称**、**节点类型**（`docker` / `mariadb-docker` / `mariadb`）、**MySQL 大版本**（`8.0` / `12.3`，为空则沿用旧复制语法）
- **HA / 复制 / 业务三类账号**与密码（平台自动在被管节点创建并周期自愈）
- **VIP**：与节点**同网段**的空闲地址（如 `192.0.2.20`）
- **掩码位**（默认 24）、**VRRP 网卡**（如 `eth0`）、**VRID**（同网段内唯一，避免与其它 keepalived 冲突）
- **VIP 端口**：业务连接 `VIP:VIP_PORT` 访问当前主库（容器化 MySQL 默认 3307，MariaDB 默认 3306）

> 多集群互不影响；每集群独立的 VIP / 账号 / 告警路由。

## 4. 添加节点与部署（节点管理）

1. 「节点管理」→ 新增节点，填：集群、IP、端口、root 账号密码、`initial_role`、`node_type`、`mysql_version`。
   - 系统做**同构校验**（引擎族一致性），并**拦截把管理库地址当业务节点**的误配。
2. 保存后平台生成**自包含目录** `generated_nodes/<ip>/`，内含 compose、配置、初始化 SQL、凭证修复 SQL（内容随 `node_type` 而异）。
3. 把该目录**整体**拷到目标机（如 `/home/docker/<ip>/`）。该目录自包含、不越级引用上级目录。
4. **目标机执行部署**：

   | 形态 | 命令 |
   |------|------|
   | `docker` | `cd /home/docker/<ip> && docker compose up -d` |
   | `mariadb-docker` | `cd /home/docker/<ip> && docker compose up -d`（**纯 compose**，无安装脚本） |
   | `mariadb` | `cd /home/docker/<ip> && sudo bash Install-ha-mariadb-Node.sh` |

   裸机安装脚本会自动完成：追加 `my.cnf` HA 片段（带备份与 `HA-MYSQL-NODE-SETUP` 标记，幂等）→ 重启 MySQL 使 GTID 生效 → 以真实 root 执行 `init_mariadb.sql`（建 `ha_monitor`/`replication`/`app` 账号，强制 `mysql_native_password`）→ 执行 `fix-node-creds.sql` 校正 → `docker compose up -d` 起 keepalived。
5. 回到平台点「刷新」或等自动发现，节点出现即纳入拓扑。

> **账号漂移处理**：若日后出现 `Access denied` / `caching_sha2` 报错，在节点本机重跑安装脚本，或在 Web「节点管理」点「下载修复 SQL」取 `fix-node-creds-<ip>.sql`，以**节点本机真实 root** 执行。

## 5. 日常监控与仪表盘

- 仪表盘按集群展示**健康卡片**（上下排列单列全宽）：角色、状态、复制延迟、IO/SQL 线程、最后心跳，以及「设为主库 / 修复复制」快捷操作；卡片顶部显示 **VIP 在线状态**（TCP 探测 `VIP:VIP_PORT`）。
- **首页全屏**布局；指标趋势、慢日志、配置漂移周期性采集。
- **空闲零写入**：监控稳态下，主机心跳、指标/漂移快照、拓扑收敛均做「变更前比对」，值未变不落库，避免持续写盘。
  - 相关限频环境变量：`HEARTBEAT_INTERVAL`(30) / `METRICS_INTERVAL`(60) / `DRIFT_INTERVAL`(300) / `TOPO_REPAIR_INTERVAL`(60) / `PUSH_MAX_INTERVAL`(300) / `PARAM_SELFHEAL_INTERVAL`(300)，单位秒。
- 点「刷新」调用 `POST /api/refresh`：仅做并发探活后立刻回读（≈单超时而非 N×超时），拓扑收敛交给后台 monitor，按钮不卡顿。

## 6. 故障切换与复制修复

**自动切换（主库失联）**
- 主库连续探活失败达阈值（`FAIL_THRESHOLD`，默认 2，约 6s）→ 决策器 `pick_best_master` 选最优从库 → 提升为主 → VIP 漂移（keepalived）→ 更新管理库 `current_master`（防脑裂仲裁源）。

**延迟 / 压力自动切换（默认关闭）**
- 除失联外，还支持按**复制延迟**或**主库压力**触发切换（`monitor._auto_switch_on_lag_or_pressure`）。
- 需在「系统设置」或经 `POST /api/setting_set` 显式开启，涉及 key：`LAG_FAILOVER_ENABLED` / `LAG_FAILOVER_SEC` / `LAG_FAILOVER_CYCLES`、`PRESSURE_FAILOVER_ENABLED` / `PRESSURE_THREADS_RUNNING` / `PRESSURE_ROW_LOCK_WAITS`、`FAILOVER_COOLDOWN_SEC`。

**手动操作**

| 操作 | 接口 | 说明 |
|------|------|------|
| 自动选主切换 | `POST /api/failover`（`cluster_id`） | 由 `pick_best_master` 选目标 |
| 指定提升 | `POST /api/failover/to`（`host`,`port`,`cluster_id`） | 手动指定某节点为主 |
| 复制自愈 | `POST /api/heal`（`host`,`port`,`cluster_id`） | SQL 线程冲突跳过 / IO 线程 GTID 缺口补齐 / 通道错位重指向；**IO 与 SQL 双线程独立自愈** |
| 节点参数自愈 | `POST /api/fix_node`（`cluster_id`,`host`,`port`） | `SET PERSIST` 固化 `gtid_mode`/`server_id` 等，重启仍生效 |
| 预检 | `POST /api/precheck` | 连通性 / 账号预检（仅告警） |

- 切换原因、前后主库记录在「切换历史」。

> 复制账号 `replication` 与 HA 账号 `ha_monitor` 由平台**周期自愈**（`ensure_ha_creds`）；若节点 root 凭证变更，用「修正节点」更新，自愈优先用 `ha_monitor`、缺权限回退 `root`。

> **注意**：v2.2.11 文档中的 `POST /api/force`（VIP/角色强制校正）**在当前版本已移除**；角色/VIP 不符请通过重新切换（`failover`）或复制自愈（`heal`）收敛。

## 7. 数据迁移（v2.4.0 新增）

「数据迁移」是**把已有数据库搬进 Custos 集群**（注意：它不是集群内主从切换，是「从外面搬进来」）。

- **入口**：左侧菜单 **数据迁移 → 迁移向导**；以往任务在 **历史迁移**。
- **支持场景**：
  - **MariaDB → MariaDB**（同引擎）：可桥接追平，业务基本不停写。
  - **MySQL 5.7 → MariaDB 12.3.3**（跨产品线）：停写拷贝，无增量追平。
  - **MySQL 8.0 → MariaDB**：**明确拒绝**（GTID 机制与字符集不兼容）。
- **强烈建议先跑预检（dry-run）**：只读探测 + 结构试运行，几秒内就能报出
  `WITH PARSER ngram` 全文索引、排序规则冲突等必炸项 —— 不要等到搬到一半才失败。
- **五步走**：录入源 → 配置目标与通道 → 执行迁移 → 停桥切换（需人工确认）→ 收尾回收。
  全程后台异步，页面显示进度 / 阶段文字 / 实时日志（刷新页面会自动接管，不会丢进度）。

> 分步图解见 [`迁移到本集群操作手册.md`](./迁移到本集群操作手册.md)。
> ⚠ 迁移**只搬数据，不搬账号权限**（`mysql` 系统库被排除），跨引擎迁移后需自行建账号。

## 8. 备份与恢复

「集群 → 备份恢复」页：

- **列出可备份库**：`GET /api/backup/databases`
- **触发备份**：`POST /api/backup/run`（`scope=all` 全库；`scope=custom` 时 `databases` 为逗号分隔库名）
- **历史列表 / 预览 / 下载 / 恢复 / 删除**：`GET /api/backup/list`、`GET /api/backup/preview`、`GET /api/backup/download`、`POST /api/backup/restore`、`POST /api/backup/delete`
- 产物落盘 `./backups/<集群>/<库>_<YYYYmmdd-HHMMSS>.sql.gz`
- 实现为**纯 Python**（镜像内无 `mysqldump`）；恢复可指定只恢复部分库到指定节点。

> 库名含 `.` 等字符时按 f-string 拼名处理，不会被 `Path.with_suffix` 截断。

## 9. 告警中心

- 探活失败、配置漂移、复制延迟超阈值等会生成告警；可自愈的自动标记 `healed`，未恢复标记 `unrecovered`。
- 收件邮箱支持「默认接收全部集群」与「按集群路由」两种。
- 告警支持确认/消音（`POST /api/alert_ack`）；可发测试邮件验证通道。

**邮箱管理接口**（v2.2.11 文档中的 `/api/alert_email*` 已废弃，改用下列）：

| 操作 | 接口 |
|------|------|
| 新增邮箱 | `POST /settings/email/add`（`email`） |
| 删除邮箱 | `POST /settings/email/delete`（`id`） |
| 设为默认 | `POST /settings/email/set_default`（`id`,`is_default`） |
| 启停接收 | `POST /settings/email/toggle`（`id`,`enabled`） |
| 绑定集群 | `POST /settings/email/map`（`id`,`cluster_ids`） |
| 发送测试邮件 | `POST /settings/test_email` |

- 告警规则（`POST /api/alert_rules`）：冷却 `cooldown`、合并 `merge`、延迟阈值 `lag_threshold`、额外收件人 `receivers`。

## 10. 在线终端、日志与设置

- **在线 SQL 终端**（`POST /api/term`）：Web 里直接对节点执行 SQL。优先用**节点 root**（可读写，支持全部 SQL）；未配置 root 密码则回退 `ha_monitor` 只读账号。支持 Tab 补全（`POST /api/term_complete`：关键字 + 库 + 表 + 列）。
- **容器 / 管理器日志**：`GET /api/srv_units` 动态列举本机可读取日志的容器，`GET /api/srv_log?svc=...` 查看；默认读管理器自身（`ha_manager`）。
- **系统设置**（`POST /settings` / `POST /api/setting_set`）：SMTP、轮询间隔、管理器内网 IP；以及自动切换 / 自动修复开关、延迟与压力阈值、保留期（指标 30 天 / 慢日志 7 天）等。配置项受**白名单**约束，非白名单 key 会被拒绝。
- **操作审计**：`GET /audit` 或 `GET /api/audit` 查看全部操作留痕。

## 11. 常见故障速查

| 现象 | 可能原因 | 处理 |
|------|----------|------|
| 节点状态 `down` 且 `err` 为账号错误 | root 凭证变更 / 账号被删 | 「修正节点」(`POST /api/fix_node`) 更新凭证，平台自愈 |
| 从库 `Slave_IO_Running: Connecting` | 主库不可达 / 复制账号密码错 | `POST /api/heal` 重建通道 |
| VIP 不漂移 | VRID 冲突 / keepalived 未起 / 网卡名错 | 检查 `vrid`、目标机 `docker ps`、`entrypoint` 自动探测的网卡名 |
| 容器化 MariaDB 起不来（权限拒绝） | 用了 UBI 镜像 / 数据目录属主不符 | 当前已统一 Debian 构建 `mariadb:12.3.3`；容器以 `user:0:0` 启动后由 entrypoint chown 降权 |
| 小内存机容器反复重启 | buffer pool 过大被 OOM | 容器化 MariaDB 默认 512M；可按内存进一步下调 |
| 页面变形 / 卡片错位 | 旧版并排网格半宽 | v2.2.11 起已改为上下排列单列全宽 |
| 刷新按钮卡顿 | 旧实现同步等待收敛 | v2.2.2 起 `/api/refresh` 只做探活后回读，收敛交给后台 |

### 11.1 复制排错要点（MariaDB 12.x / GTID）

| 现象 | 根因 | 处理 |
|------|------|------|
| 主库永远是只读、VIP 离线 | MariaDB 10.11+ 执行 `SET GLOBAL read_only=0` 需 `READ_ONLY ADMIN` 权限，`ha_monitor` 未授该权限会报 1227 | 授权已并入 `ha_grant`：节点本机执行 `GRANT READ_ONLY ADMIN ON *.* TO 'ha_monitor'@'%'; FLUSH PRIVILEGES;`（或在节点跑 `fix-node-creds.sql`） |
| 从库复制报 1062 卡死 | `ha_local.state` 是**节点本地**状态表，写它时未禁 binlog，被复制到从库与本地行冲突 | 写 `ha_local` 时以 `SET SESSION sql_log_bin=0` 包裹；挂载复制时 `CHANGE REPLICATION FILTER REPLICATE_IGNORE_DB=(ha_local)` 双保险 |
| 跳过冲突事务报 1966 | **并行复制 + 多域 GTID** 下禁止 `sql_slave_skip_counter` | 改为显式设置 `@@gtid_slave_pos` 跳到指定位置之后 |
| 新建/重装节点报 `Table 'xxx' doesn't exist` | 该库的表是在主库**绕开 binlog** 建的（如 `sql_log_bin=0` 或建在开启复制之前），binlog 里没有 `CREATE TABLE`；而新节点无基线数据种子，重放历史行事件时表不存在 | 先从主库做一次基线全量种子再挂载复制：`mariadb-dump --single-transaction --gtid --all-databases` 灌入节点，再 `START REPLICA`（位置由 dump 内的 `gtid_slave_pos` 对齐） |
| 复制报 1677 列类型转换失败 | 主从同表列类型不一致（如主 `longblob`、从 `text`，窄化转换） | 对齐从库列类型与主库一致（改宽不丢数据），再启动复制 |

## 12. 版本与升级

- **升级管理端**：`./scripts/deploy.sh up -d --build`。`init_schema()` 会自动补齐表结构与字段（含旧版兼容迁移），**无需手工建表**。
- **升级节点**：重新生成节点目录并重新部署即可；节点数据目录保留，不受影响。
  - 容器化 MariaDB 自 v2.2.13 起数据目录为 `/data/custos-ha/mariadb12`（原 `/data/mariadb`），**旧数据不会自动迁移**，需按需手动处理。
- 版本号唯一来源为 `.env` 的 `VERSION=`；`scripts/deploy.sh` / `Makefile` 从该文件读取后构建，并由 compose 以环境变量 `VERSION` 注入容器（应用经 `config.APP_VERSION` 读取）。`app/VERSION` 文件已于 v2.2.20 废弃删除。

## 13. 安全提示

- 节点部署资源统一来自 `app/node_assets/`；生成的 `generated_nodes/<ip>/` 内含**明文密码**（`ha_check.conf`、`init_mariadb.sql`、`fix-node-creds.sql` 等），仅限目标节点本机使用，勿提交到版本库（该目录已 gitignore）。
- `generated_nodes/` 与 `data/` 均已 gitignore。
- 管理端 `SECRET_KEY` / `WEB_PASS` 生产环境务必修改（默认 `admin`/`admin`）。
- 所有服务账号（`ha_monitor` / `replication` / `app`）统一强制 `mysql_native_password`，以兼容 MySQL 8.0 默认 `caching_sha2_password` 在**非 TLS 复制**下报 `Authentication requires secure connection` 的问题。
